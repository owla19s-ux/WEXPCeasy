## 一、产品定位

WEX 是面向长期工作的**跨平台联通、调度、交互、知识与生产管理系统**。它让人、AI、工具、外部服务、资料、任务和专业视图在可控边界下协作。它不是只有聊天窗口的 AI 客户端，也不是自建完整 Agent 执行平台，更不是只为软件开发设计的项目管理工具。

核心理念是**工具为人服务**：用户可以先从对话或一个轻量工作对象开始，按需组合模型、连接器、Agent、资料、工作流及交互界面；扩展工作能力时不必整套迁移工作环境。

当前阶段以**个人自用、Windows PC 优先**为确定目标；Android 旧原型暂停。小范围合作、公众发行、云端部署与跨设备使用是可选的发展阶段，不作为当前必须达成的承诺。

### 为什么需要它

现有软件往往分别处理 AI 对话、文件管理、代码工具、自动化、知识库、任务或内容制作。复杂工作容易出现资料散落、重复配置、手工中转、外部执行结果难以验证以及更换工具后无法安全接续的问题。WEX 试图提供长期组织与受控连接的底座，而不是重写每一种专业工具。

### 基础原则

1. **Context 可独立存在、能力按需组合**。不强制以项目、目录、Agent、模板或工作流作为前置。
2. **数据权威归属单一**。业务数据归具体模块维护；跨模块通过公开能力协作，不建立全局业务状态总管。
3. **关联不等于授权**。选择一个模型、工具、角色、插件或 Context 资源，仅记录组合意图，不自动获得调用资格。
4. **事实分级**。模型建议、工具操作尝试、外部回执、产物验证和最终验收分别记录。
5. **研究、已批准设计、实际代码和测试证据分离**。实验通过不代表正式产品实现；未来构想不自动进入当前版本。
6. **先有基本可用产品，再发展复杂能力**。不会为了未来所有场景一次性构建全部基础设施。

## 二、WEX 的总体组成

| 系统 | 负责什么 | 不负责什么 |
|---|---|---|
| Space / Context | 工作组织、身份、资源地址和能力关联 | 复制 AI、连接器、任务或权限内部数据 |
| Conversations | 会话、消息、段落与编辑重发、人机讨论 | 将聊天文本当成外部操作事实 |
| AI / Roles | Agent 配置、角色、职责、模型引用 | 接管 Provider 协议或以角色名称发放权限 |
| Connections | 能力接入、配置、受控调用、Operation 回执 | 将所有第三方服务内部状态搬进 WEX |
| Workflows | 工作流定义、任务相关业务记录、产物引用和验证/验收事实 | 图形渲染或连接器的真实外部操作 |
| Scheduler | 独立任务协调、等待、派发、恢复、资源冲突 | 充当工作流编辑器或直接拥有所有外部工具 |
| Views / UI | 多视角呈现、布局、交互和受控业务编辑入口 | 维护第二份权威业务状态 |
| Permissions | 主体、入口、范围、操作授权及审计 | 由 Agent 自行决定权限 |
| Shared / App | 存储和凭证等技术基件、可信宿主、生命周期及装配 | 把各模块业务逻辑堆入公共层 |
| Plugins / DSH | WEX 自有扩展研究、DSH 原生插件兼容宿主 | 代替 Connections 或外部 DSH Agent |

这张表是职责图，不是要求每次操作必须依次经过这些模块。普通对话和单次受控工具调用无需先创建任务或工作流。

## 三、Space、Space 类别、Group 与 Context

**产品说明顺序：Space → Space 类别 → Group → Context。** 这是概念组织顺序，不代表所有对象都构成严格的物理父子目录层级。

### 3.1 Space：工作组织入口

Space 用于组织用户的工作内容及其关联的 Context，可以具有名称、说明、独立身份以及可选的工作区目录登记。Space 本身不是文件目录；移动、重命名和工作区失联不应直接改变其稳定身份或删除工作资料。

用户可以建立小说创作、软件开发、信息收集等 Space，也可以有多个相近用途的 Space。

### 3.2 Space 类别：对 Space 分类

Space 类别用于组织多个 Space，例如个人、公司、公开、实验等。**类别不是物理目录、租户、企业账号或权限身份**。更改类别不应隐式搬迁资料。类别的删除与复杂归属策略尚须单独确定。

### 3.3 Group：可选的组织分组

Group 在 Space 中提供进一步整理能力，例如软件开发 Space 下的“当前项目／实验／归档参考”，小说 Space 下的“作品／人物／资料”。用户无需先建 Group 才能创建或使用 Context。Group 的排序、命名及组织调整不应自动修改外部资源。

### 3.4 Context：可独立存在的长期工作对象

**Context 是围绕某项工作、目标、内容或持续活动组织的可扩展工作环境。** 它可以在没有 Space、Group、Agent、Task、模板和工作流的情况下建立，并具有稳定 ID、自身配置、独立的数据定位及修订信息。

Context **不等于**：本地文件夹、GitHub 仓库、普通软件项目、一段聊天、一张任务卡、模板或工作流。它可以由少量资料与对话起步，逐渐增加工具、Agent、视图及专业能力。

同一个 Context 可以根据产品需要出现在不同的组织入口中，而不复制出互相矛盾的权威本体。相关关系如何实现应由数据模型判断，**用户原始产品设计并没有把 `Placement` 作为第五层组织概念**；目前仓库 `space/README.md` 采用 Placement 表示内部放置关系，只是现行技术方案。正式产品说明不应把它当成用户必须理解、创建和管理的第五种组织层级。是否保留该内部模型，留给 Space 设计/实现审查，不在本文擅自要求删除代码。

### 3.5 Context 主地址及多个附加地址

Context 可以设置明确的**主地址**，并独立添加多条附加资源记录。每条附加地址可包含**名称、地址、备注、类型／来源和用途**。例如：

| 资源 | 地址示例 | 用途 |
|---|---|---|
| 主地址 | GitHub 代码仓库 URL | 主要工作对象 |
| 附加地址 A | Windows 本地源码目录 | 实际编辑／操作 |
| 附加地址 B | Windows 构建目录 | 编译产出 |
| 附加地址 C | 本地或远端文档 | 需求／参考 |
| 附加地址 D | 远端资源 | 外部资料或交付 |

**主地址、操作地址、产出地址、参考资料地址、Context 自身记录目录可以完全不同**，不必同盘、同目录或处于父子关系。用途可扩展，不要将地址集合压成一个 `projectPath`。主地址改变不应改变 Context ID、自动搬迁文件或触发同步。

登记地址和验证目标是两个操作：可以先保存未验证地址，断网或目录尚未产生时不应凭空宣告其无效并删除；但未验证的地址也不能冒充已获准访问的真实资源。资源的真实身份、可用性和实际操作由对应 owner/适配器核验。

### 3.6 Context 添加资源、Agent、角色、API 与工具

Context 可以显式引用 API/Model 配置、Role、Agent、文件与远端资源、连接器能力，以及未来的工作流、调度器和专业视图。**引用、配置选择和本次执行绑定是三个不同层面**：

- 引用：记录“这个 Context 关联了什么”。
- 配置选择：记录经过允许的 Context 局部选择；全局 Provider、角色或连接配置仍归各自 owner。
- 执行绑定：具体一次对话或任务实际选什么、能否调用，由消费方与 Permissions 判断。

工具可以在一个 Context 启用、另一个 Context 停用；Context 选择工具不等于全局安装、启动执行或权限自动放行。凭证不能作为明文复制进 Context。

### 3.7 软件开发 Context 实例

用户创建 WEX 软件开发 Context，主地址指定 GitHub 仓库，添加本地代码目录、构建产物目录、需求说明文档；关联模型、角色、本地文件／编译及 GitHub 能力。用户可以通过对话规划工作，在本地编辑、编译和测试，再通过 GitHub 能力把**明确选择的成果**同步到主仓。操作、产出、主地址彼此独立。同步冲突及外部回执由连接模块处理，Context 只维护组织与组合事实。

## 四、AI、Agent、岗位、角色和模型

AI 是协作能力，不是全系统唯一控制中心。需要区分：

- **岗位**：主 AI、秘书、执行、审查等工作分工位置；具体数量不是固定四个。
- **角色**：可复用的行为、知识、职责或风格配置。
- **Agent**：参与工作的 AI 配置或执行主体。
- **Provider/Model**：实际模型服务与型号。
- **Connection**：调用模型或其他服务的具体连接配置。
- **运行会话**：某次实际互动或外部 Agent Session。

同一角色可以被多个 Agent 使用；更换模型不自动更换职责、身份或授权。外部 Agent 的内部循环和 Session 不应被 WEX 的 Agent 配置表冒充。

长期支持主 AI、秘书 AI、执行 AI 和独立审查角色协作，但**0.1.1 不交付完整多 Agent 自动派工**。早期重点是可复用配置、职责关联、模型选择和真实对话链路。角色记忆、共享经验库和完整内部 Agent 自主循环需独立研究。

## 五、普通对话与增强交互

用户打开 WEX 就可以开始普通聊天，不需要预先建 Space、Context、工作流或 Task。Conversations 管理会话、消息、历史、编辑重发、段落选择/引用和适用的分支交互；实际 Provider 调用、流式协议与回执由 Connections/API 完成。

重要研究方向是**段落式交互**：当 AI 一次输出多个问题、建议或设计段落时，用户能够选择某段单独确认、排除、补充、修改重发或继续局部讨论。其目的不只是分叉聊天，还可以把讨论定位到具体需求、架构模块或功能对象，例如从架构树中选择一个模块，直接查看其约束、接口、依赖并围绕它讨论。普通消息和专业对象的业务修改仍要走各自受控入口。

会话历史、工具调用事实、Task 检查点与模型隐藏上下文必须分开。新会话可以重新读取可访问的记录，但不应宣称旧模型内部状态已经自动恢复。

## 六、连接器：内置能力与公共交换

Connections 是 WEX 的能力接入、配置和受控操作边界，可把内部必要能力和外部服务连接起来；不是要求所有模块内部函数调用强制绕行的总线。

### 6.1 内置连接器／内置能力

用户从功能角度可以称 API、GitHub、本地文件工具、DSH 连接器为内置能力；从工程角度它们是**随产品配置和装配的适配模块，不等于必须通过动态插件加载器运行的插件包**。

- **API**：Provider/Model/Key 安全引用、参数、流式响应、取消、错误及适用的工具调用；Pi AI 等 SDK 可以验证后按需复用，但不预设完全兼容。
- **GitHub**：仓库、分支、提交、PR、Issue、Actions、文件和同步能力；实际操作需权限及冲突判断。
- **本地文件与开发工具**：目录/文件、Git、编译与测试能力；明确输入、工作位置、输出及访问范围。
- **DSH 连接器**：与**外部独立运行的 DSH Agent**连接，交换任务、结果和观察信息；不自动接管 DSH 内部执行循环。

Connections 公共边界保留 Operation/attempt、调用依据、失败及结果未知的观察；不能因为回执持久化成功就宣称外部动作成功。发现服务或插件能力不代表自动授权。

## 七、WEX 自有插件机制与 DSH 原生插件兼容机制

这是两条不同路线，另须区分“外部 DSH Agent 连接器”。

| 路线 | 主要职责 | 当前边界 |
|---|---|---|
| WEX 自有动态插件机制（`plugins/`） | 未来安装、依赖、生命周期、能力注册、权限、配置面板和 UI 扩展 | 仍为预留研究，没有产品级通用动态加载器 |
| DSH 原生插件兼容宿主（`dsh/`） | 运行符合已验证 DSH 插件机制及依赖条件的原生插件 | 已有 Cordis Core + Loader 独立实验，尚未完成 WEX/Windows 正式集成 |
| DSH 原生插件 | 由 DSH 插件协议定义的具体扩展功能 | 必须满足实际依赖，不承诺所有插件都能运行 |
| 外部 DSH Agent 连接器（`connections/dsh/`） | 和独立运行的 DSH Agent 通信 | 与原生插件宿主平行，互不作为启动前置 |
| API/GitHub 等内置连接器 | 提供常用服务或工具适配 | 不是 WEX 动态插件机制已实现的证据 |

DSH 兼容宿主实验已验证部分真实磁盘插件加载、服务注册、依赖等待、配置重载、卸载与重载，并保持版本锁定；**这不等于**完整 DSH Bundle/Profile/商店、任意插件、Windows/Electron 或 WEX 正式集成通过。某插件依赖 `sessions`、`tools`、`llm` 等 Service 时，应报告真实缺失，按需补最小兼容、使用外部连接器或明确不支持，不为兼容一个插件就无条件搬入整个 DSH Agent 运行时。

DSH 同进程 Cordis/Loader **不是系统安全沙箱**。安装管理、权限、插件回调、进程隔离与受控能力暴露均需分别验证。WEX 自有插件与 DSH 原生插件可研究复用部分底层技术，但不能因底层同源而混成同一安装清单或插件协议。

## 八、工作流、自由格子交互、独立调度器、多视图：四种不同职责

这四者可能一起出现在用户界面，但**不是同一个功能**。

### 8.1 工作流：工作的业务定义

定义工作步骤、明确的执行依赖、输入输出、条件、任务交接、产物及验证要求。工作流定义／草稿修订与正在运行的任务、操作事实不能混成画布库的一份 JSON。普通对话和独立任务无需创建工作流。

### 8.2 自由格子：可视化组织与节点工作界面

用户最初讨论的是**自由放置、编辑、自动整理的格子节点**，连线优先直线和转角，颜色或其他视觉信息表达不同状态；节点能按需要展开为摘要、局部操作、完整工作台或多节点组合观察。软件开发可以展开代码、测试与审查界面，未来图像／视频节点可能需要更复杂的素材及共享预览。

**自由格子是一种交互形式，不应被简单等同于完整工作流引擎。** 一条视觉连线不必然意味着执行依赖：架构图、功能树的连线可能是业务引用或模块依赖。工作流的运行语义必须另行明确定义。

当前仓库 `workflows/grid/` 把自由格子放在工作流专属目录，负责工作流节点/定义/编辑；用户此前也讨论过将相似图形交互用于架构树、功能树等专业视图。**是否抽取可复用的通用自由格子交互底座尚未冻结**，不能凭现有目录反向限制产品愿景，也不能未经验证直接要求所有专业视图共用同一引擎。

### 8.3 调度器：决定何时、由谁、以什么资源协调执行

独立顶层 `scheduler/` 负责派发、等待、重试、取消、恢复、资源冲突与运行进度；可以服务独立任务、多个 Context 或多个工作流，**不以打开自由格子编辑器为前置**。连接器负责实际外部操作及回执，权限域负责授权；任务和验收业务由各自 owner 维护。

例如在普通对话中要求编译项目，未来可以协调独立任务，不需先在画布上放一个“编译节点”。

### 8.4 多视图：从不同业务角度观察与操作

同一 Context 可同时拥有对话、文件、架构树、需求树、功能树、任务、验证、工作流画布等视图。视图呈现和映射业务事实，但不是第二份业务数据库，也不是必然执行任务的图。

同一任务可以在执行视图显示“结束”，在验证视图显示“待核验”，在验收视图显示“未接受”；这些属于不同事实维度，而不是必须同步的单一颜色状态。

用户调整的基础多视图布局需保存与恢复。**单窗口多 Context、多窗口各自承载 Context、混合模式仍未最终决定**。早期 Windows UI 不必追求复杂的个人定制工作台。

### 8.5 四者的组合案例

用户从架构视图分析依赖，通过对话针对某个模块局部讨论；随后建立或修改工作流定义，在自由格子上查看工作步骤及节点工作台。调度器按显式规则协调任务；连接器调用 GitHub、本地工具等能力并保留回执；多视图展示执行、测试、审查与最终验收。

这是一种可能的组合，不代表所有操作都必须经过画布或调度器。

## 九、任务、操作回执、验证和最终验收

Task 是独立的工作单元，可来源于用户指令、对话或工作流。长任务需要可以识别目标、输入、配置修订、负责人、尝试记录、产物、验证、审查、验收及恢复检查点；不能把聊天摘要当成完整任务状态。

必须严格区分：
1. 用户或 AI **提出操作**；
2. 连接器**实际派发并观察到结果**，有可能结果未知；
3. 产物**被验证**，需绑定来源版本和验证环境；
4. 用户或指定的独立主体**最终验收**。

AI 自报 completed、测试命令退出 0、审查建议和最终接受不是同一件事。系统关闭、网络失联、外部副作用结果未知时，应先核对原 Operation 和事实，不应盲目自动重做可能造成重复写入的动作。

## 十、权限、安全与受控执行

权限可依据模块启用、全局访问、对话授权，以及主体、入口、Context/任务范围、操作及资源等约束分层判断。未授权入口默认拒绝；模型输出、角色名称、Context 工具关联和插件发现不构成授权。

此前讨论的对话四级授权、主 AI/秘书 AI 共享、由用户主动设置的对话等级、工作流节点预授权及启动检查，是产品决策与待完善政策的一部分；具体高风险动作（Shell、插件安装、权限、凭证修改等）的最终边界不能由施工者根据候选草案擅自放开。自动化及外部 Agent 对用户资料的调用应按实际入口与操作范围重新核验。

## 十一、数据、知识与 Windows 部署

WEX 区分**程序安装目录、用户选择的公共数据根、Space 工作区、独立 Context 记录目录、外部资源与系统必须管理的凭证/注册信息**。希望大部分可迁移资料保存在用户选择的位置，避免全部散落在系统盘。Space/Context 的组织引用并不自动执行物理迁移。

公共数据根可保存配置、索引、必要账本及诊断信息；普通日志和正式业务记录分开。目录失联时保留定位与诊断，不创建同名空对象冒充恢复。Windows 安装、重装、恢复、凭证重新接入、升级和损坏恢复仍需要实际验证。

知识来源、Conversation 历史、Task 检查点、操作记录和 Agent 长期记忆是不同数据；长期共享记忆与策略库的 owner、权限和产品形态仍待确定。一个 Context 可以按权限引用另一个 Context 的资源，但关联本身不授予其全部资料访问权。

## 十二、模板与跨领域扩展

模板可以是**工具 + 工作流 + 专业视图 + 适用 AI 配置**的组合，不是 Context 的唯一类型，也不要求用户为了使用 Context 先安装完整模板。

- 软件开发：GitHub、本地工具、编译、架构树、代码与审查视图。
- 小说世界：文本创作、世界观、参考资料、角色和内容生成能力。
- 人物角色：人物资料、图像、声音、视频等逐步扩展。
- 信息收集：资料来源、查询、整理、核验与长期追踪。
- 其他工作：按需复用上述工具与工作流能力。

例如小说 Context 先只有文本，后来关联角色系统，再添加图像、声音、视频、漫剧甚至实体周边生产服务，**无需每新增一种能力就重新设计 Space–Context 组织底座**。但跨 Context 数据共享、模板继承和能力覆盖规则仍需具体确定。

## 十三、Windows 应用与交付阶段

当前技术路线以 **TypeScript、Electron、React** 为优先；领域代码不能因为宿主使用 React 就全部耦合到 UI。App 提供应用启动、模块装配、生命周期、Preload/IPC 安全边界、关闭及故障恢复。

### 0.1.1：基础 Windows 客户端

现行获批范围：Space/Context 基础组织及资源/工具关联；Agent/角色/模型绑定；API Provider/Model/Key/参数/流式调用；普通对话、基础编辑重发、历史恢复；Connections 基础受控调用；Permissions；配置/索引/日志；App 生命周期；Electron/React 基础界面；**同一 Context 的基础多视图与布局保存恢复**；安装及数据恢复。

三批实施：**B1 基础业务模块 → B2 跨模块基础闭环 → B3 UI 接线与 Windows 交付验收**。既有 shared、permissions、app、connections/src 有产品基础代码和测试记录，其他领域需逐模块检查最新状态。现有 Electron 和工作流原型不是正式 Windows 实机产品；不能未测就声称完成。

### 0.1.2：明确后置

**自由格子工作流及其可视化、正式调度器、DSH 原生插件系统产品化、DSH 连接器与外部 Agent 执行闭环**。0.1.1 不得以这些能力作为交付依赖。WEX 自有完整动态插件机制更不能被假定为已经获批的 0.1.1 功能。

### 长期阶段

第一阶段个人自用；小范围协作及公众发行可选，可能不启动。云端长期运行、跨设备同步、企业身份、完整多 Agent 自动化、长期记忆及复杂创作工作台均需分阶段验证，而非一次铺满。

## 十五、需进一步核对的三类关键问题（本说明的明确保留项）

### A. Space 的 Placement：产品概念与内部模型分离

用户原始设计强调 **Space → Space 类别 → Group → Context**，未提出 Placement 为第五层产品对象。仓库当前 Space 规范采用 Placement 表达 Context 在不同 Space/Group 中的放置关系，有其实现动机，但**不能据此反向改写用户产品概念**。

后续核对：多处引用是否必要、如何持久化、如何解除关系且不删除本体、用户 UI 中是否只呈现自然的组织操作。本文暂不擅自删除内部机制，也不把它列成用户必须管理的独立层级。

### B. 自由格子：交互形式、工作流业务、通用视图基础需要继续分清

用户最初提出自由编辑格子、正交连线、自动整理、节点展开与专业工作界面；相关交互可能扩展到架构树、功能树和其他专业视图。仓库目前 `workflows/grid/` 主要面向工作流。这不足以证明整个自由格子构想只能属于工作流业务。

后续核对：是否抽象可复用图形交互能力、哪些节点视图使用相同组件、业务对象及关系的权威 owner 如何隔离。**不预先决定所有视图共用一套引擎，也不把所有视图强塞进工作流调度器。**

### C. 插件：内置连接器、WEX 自有插件和 DSH 原生机制必须分别说明

用户口语中称 API/GitHub/DSH 连接器为“内置插件”没有问题，但工程上需要区分内置适配能力、未来 WEX 动态插件、DSH 原生插件与其兼容宿主、以及外部 DSH Agent 连接器。四者的安装、生命周期、权限、执行事实及版本验收路径均不同。

后续核对：WEX 自有插件最终协议与动态装载方式、DSH 兼容 Service 的范围、是否采用独立进程、如何通过 Connections 公共能力暴露和授权。不能以 DSH hello 插件验证代替所有正式产品验收。

## 总结

WEX 从一个可运行的 Windows AI 客户端、可靠的 Context 组织与基础连接起步，逐步成为允许用户自由组合 AI、工具、资源、交互、工作流与调度能力的长期工作环境。

**Space 组织工作；Context 承载独立且可扩展的工作对象；AI 和对话辅助理解与操作；Connections 实现受控能力交换；插件提供进一步扩展；工作流定义过程；调度器协调执行；多视图提供不同角度的观察与操作；权限、回执及验收保证实际结果可查。**

本说明为**待用户继续补充和确认的 V0.1 草案**，不自动冻结未决架构，不扩大版本范围，也不宣称未来能力已经实现。
