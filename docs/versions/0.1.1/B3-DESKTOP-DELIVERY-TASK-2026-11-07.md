## 一、目标与执行边界

目标是在不重写已有业务模块的前提下，将现有 **Space/Context → Agent/角色/模型 → API/Connections → Conversations** 基础能力，逐步接成可供用户实际操作、保存及恢复的 Windows Electron/React 客户端，并完成相应验收。

- **按模块 owner 连续施工**：每个 owner 内持续完成查缺口、实现、单测、修复、复验与回执；不因一个文件、一次提交或一次回复要求用户反复发“继续”。需要其他 owner 的新接口时列出最小契约与依赖，按模块边界分别实施。
- **不得擅自改文档**：一般代码施工模式只修改已授权产品源码/测试；计划、README、CONTRACT 由验收/文档维护模式更新。本文件属用户明确要求的任务文档维护，不表示后续施工自动取得文档修改权。
- **事实与验收分离**：代码存在、自动测试通过、真实外部服务调用、Windows 实机使用、安装交付五者分别记录。不得把 Xvfb/CI 启动与截图冒充完整可用 UI，也不得用本地测试 Provider 冒充第三方 Provider 验收。
- **原定阶段不变**：B1 为独立模块基础与公开契约，B2 为模块组合闭环，B3 为正式 UI/Windows 交付；已实现能力仅补真实缺口。不得未经确认将 B1/B2 的残余缺陷隐藏为 B3 通过。
- **明确排除**：自由格子工作流、正式调度器、DSH 插件产品化、DSH 外部 Agent 连接器及执行闭环均为 0.1.2；复杂对话局部分支交互若机制未冻结，不强行纳入本版验收。

## 三、分模块任务与验收

### D-01｜桌面可信入口、IPC 与授权接线（归 B3-01，优先）

**Owner**：`app`（可信装配、preload、IPC、生命周期）与 `permissions`（已有权限决策 owner），`UI` 只消费受限的可序列化接口。

- 复查 `app/src/desktop-*.ts`、`app/desktop/preload.cjs`、`UI/src/index.ts`，包括已有 `desktop-space.ts` 及其实际接线情况。
- 基于已有主进程模块公开端口，逐步增加**具体、最小、可审计**的业务 IPC：Space、AI/Agent、API、Conversations、连接配置、必要受控资源操作；请求/结果结构确定后分别测试。
- 每个入口绑定 Electron 当前可信窗口/帧身份，校验输入、当前授权、请求作用域、能力边界与取消/关闭状态；不能由 Renderer 自报用户身份、权限等级、Context 授权或文件真实路径。
- 用户主动授权、确认与撤权反馈应通过已定三层权限及对话权限规则完成；高风险未决政策不得猜测默认允许。正式用户入口不能一直使用全部拒绝的演示 trust 配置，也不能为打通 UI 直接改成全允许。
- 不暴露 Node/FS/数据库/API Key、模块服务实例或可任意执行的 IPC 调度器到 Renderer；不在 Electron 主进程重写业务 owner 的领域规则。
- **验收**：可信窗口合法请求能执行最小获准操作；跨窗口/伪帧、参数注入、撤权/重放、关闭/重启、拒绝与错误反馈可复现；宿主装配、模块测试与边界检查通过。

### D-02｜Space / Context 桌面页面（归 B3-02）

**Owner**：`UI/space` 的页面交互，`space` 持有数据与组织规则，`app` 提供已审查 IPC。

- **先复核现成实现**：`UI/src/space.tsx` 与 `app/src/desktop-space.ts` 已在编写任务时存在，结合测试确认“实际可使用的部分”，禁止按历史“无 UI”重做。
- 基本操作：Space **类别 → Space → Group → Context** 的导航、创建、编辑、组织和切换；Context ID 不随 Group 迁移改变；不得新增 Placement 产品实体或把 Space 等同物理 workspace。
- 支持 Context 关联地址的**主地址及多条附加地址**（名称、地址、备注、用途），区分参考、操作、产出等用途；不得假设 GitHub 主仓与本地工作目录必为同一地址。
- Context 详情中的文件/目录列表和展开内容必须经 Local 或对应连接器的受控读取；关联文件不等于导入副本；页面不得直接扫描任意目录。工具/能力关联展示真实来源和可用状态，不因“可见”直接授予执行权。
- 目录选择使用可信原生确认与目录选择入口；失联/版本变化、冲突、撤权、重启恢复给出明确反馈。
- **验收**：从真实 Electron 窗口完成创建、编辑、组织、切换、地址和目录引用；重启后同一 Context ID 与组织、资源引用可恢复；非法路径、越权、并发/旧修订被拒绝。

### D-03｜API Provider / Model / Key / 参数的可用配置（归 B3-04、B1-03 收口）

**Owner**：`connections/api`（协议与配置）、凭证实际 owner、模块专属 UI、`app` 窄 IPC。

- 复用现有 Provider/Connection/Model、参数、模型观察、准备/发送、非流式与 SSE、取消/超时/失败、工具**提议**与续接、恢复代码。
- 提供增删改查连接的 UI：可命名 Provider/连接、地址、模型、常用参数和模型能力/可用性反馈；接入 API Key 的**受信录入、保管与绑定流程**，只保存凭证引用，不把 Key 放进 Renderer 可读配置、Operation、日志或 Space。
- 配置项是否支持特定 Provider 的能力须按实际协议与测试声明；Pi AI 隔离实验不授权替代现有协议实现。
- **验收**：用户在桌面完成配置 → 选模型 → 实际请求 → 流式显示/取消/失败提示 → 重启恢复；测试 Provider 与实际外部 Provider 分开报告，未获批准不调用收费端点。

### D-04｜Agent / 岗位 / 角色的选择与配置（归 B3-04）

**Owner**：`AI`、模块 UI，`space` 持有 Context 引用，`app` 接线。

- 允许用户建立/编辑/选择岗位、角色、Agent、模型与连接的组合；不混淆岗位、角色、Agent、API Provider、Context 和会话，不复制凭证和权限状态。
- Context 只保存获准关联及配置选择，不凭关联隐式赋予权限；修改模型/角色不能偷偷改用旧会话授权。
- **验收**：UI 建立配置、从 Context 选择并使用、编辑冲突与重启恢复；角色提示词对单次生成明确绑定且不得越权。

### D-05｜Conversations 正式对话页（归 B3-03）

**Owner**：`conversations` 负责消息/会话/生成状态；`UI/conversation` 负责页面；API 负责 Provider 协议；Connections 负责真实副作用 Operation。

- 对话页完成会话列表、输入、消息显示、历史切换/恢复、Agent/模型选择、流式响应、停止/失败/未知状态与重试提示。
- 保留已确认的**段落级选择、追加、修改重发**基础交互；编辑快照、原消息与生成回执可追溯，避免用渲染文本覆盖权威历史。
- 基础文件输入、原生文件选择、拖入/粘贴、预览/移除及来源提示需经受控 Local/Connections 读取；区分本轮临时附件、外部原文件关联和用户主动导入持久副本。若某项导入策略未定，仅冻结受影响操作，不阻断纯文本对话。
- 对模型生成的工具调用只呈现**待授权提议**，不让模型输出直接在 Renderer/IPC 执行高权限动作。
- **验收**：真实 UI 完成多轮输入、流式显示、取消、段落编辑与重发；对话和 Generation 重启恢复，拒绝/断连/结果未知保留 Operation 依据，不盲重试副作用。
- **非本版强制**：针对段落的复杂局部分支/多焦点讨论机制若尚未定稿，不借基础 Segment 实现假称已完成。

### D-06｜GitHub 官方能力与连接器源码归位（归 B1-06 / B3-05，可独立施工）

### M-01｜连接器子模块 owner 隔离（高优先级；D-06A 前置验收）

- **已核对事实**：`tools/check-boundaries.mjs` 当前按路径第一级划分 owner；`connections/api`、`connections/github`、`connections/local` 可能被当成同一个 `connections` 模块，无法充分识别连接器之间的私有源码引用。
- **施工要求**：在现有边界检查机制上增加细粒度 owner 识别及对应正反例测试；`connections/src/` 为公共连接边界，`connections/api/`、`connections/github/`、`connections/local/` 为不同 owner。跨 owner 只走其正式公开端口，不直接读取其他连接器内部文件；也不得通过路径别名、类型导入、动态导入绕过。**不新增一套插件框架或依赖系统**。
- **归属**：边界检查脚本/测试归 `tools/` 工程约束维护；Codex 开始 D-06A 之前应核查此门槛。若单独授权仅限 `connections/github/`，则先记录需由工具 owner 完成的最小更改，不得擅自跨 owner 写入；获得相应施工授权后补规则、测试，再进入完整的官方组件集成验收。
- **验收**：允许公共正式出口依赖；必须拒绝 `github` ↔ `api/local` 私有交叉导入及非法反向依赖，并运行实际全仓边界检查、独立测试。将运行命令和结果写入回执。

### M-02｜App 装配边界，防止领域逻辑向宿主聚集（高优先级约束）

- `app/src/foundations.ts` 已集中装配 Shared、Permissions、Space、API、AI、Conversations、Connections、GitHub 与 Local。**集中依赖装配本身允许**，不能仅因文件较长就机械拆文件；真正边界是不得将领域规则、协议实现、连接器进程通信、配置存储权威移入 `app`。
- GitHub MCP Server 的安装/启动/关闭与协议适配归 `connections/github/`，App 只经其公开入口选择适配器并托管必要生命周期；不在 `foundations.ts` 追加第二套 GitHub 协议、凭证、权限或 Operation 状态。
- **验收**：检查新增 import、修改文件、公开端口以及装配/停机测试；若不得不扩展 App，只做最小接线，不借此次施工进行全局重构。

### M-03｜UI／桌面 IPC 契约解耦（中优先级；随 D-01/D-03/D-05 施工）

- **已核对事实**：`app/src/desktop-runtime.ts`、`desktop-space.ts`、`desktop-api.ts` 的部分类型来自 `UI/src/index.ts`。当前属于类型层耦合，不等同于在主进程运行 React；但不宜让未来宿主契约随着页面实现任意扩张。
- 逐步让可序列化 IPC 请求/响应契约由双方可引用的中立、无特权公共入口维护；**先核对现有约定及消费方，需新建或迁移契约时只做必要最小修改，不建立新全局业务状态模块**。业务语义仍归各自领域 owner，Renderer 不可直接导入 Node、Electron 特权能力或领域私有实现。
- **验收**：静态依赖方向和 Renderer 特权负例、输入验证、跨窗口/伪帧、撤权/关闭后拒绝、兼容测试通过；不因重构接口名导致已有 Space UI 退化。

### M-04｜区分“有适配代码”和“正式入口已接线”（中优先级）

- **已核对事实**：`app/src/desktop-api.ts` 有 API 桌面适配代码，但审查基线的 `app/src/desktop-runtime.ts`、`app/desktop/preload.cjs` 及 `UI/src/renderer.tsx` 尚不能据此认定 API/Agent/Conversations 已有完整正式操作入口。
- **施工要求**：每个 D-01～D-09 任务分别核对“领域公开能力 → 可信宿主装配 → IPC/preload 最小暴露 → 正式 UI 触发 → 授权/持久化/恢复 → 实测回执”；缺任何一步不得标成用户可用。
- **验收**：至少用真实 Electron 窗口验证本版必需流程；mock/单模块测试、Linux Xvfb 宿主测试、Windows 实机和安装交付分别记录，不相互冒充。

### 模块化审查退出条件

1. `tools/check-boundaries.mjs` 能按子连接器 owner 拒绝私有跨域依赖，相关测试及全仓边界检查成功，或有明确阻塞说明且不得将 D-06A 的完整验收标通过。
2. 每次新增模块接线均明确源码 owner、公开端口及消费方，`app` 不复制业务逻辑、权限、凭证或账本。
3. IPC 类型与页面实现保持可审查的依赖方向，正式 Renderer 不持有主进程特权能力。
4. 单模块通过、跨模块测试通过、UI 可操作、Windows 实机完成四种结论分别附证据；不得将任何一种自动推导为其余三种。

## 五、依赖顺序（不强制每个功能一 Commit）

1. **先排除最新 main 的实际 CI 回归**；在 `app/desktop-space`、`UI/space` 的已有实现上修复，而非重建。
2. D-01 可信 IPC/权限接口；D-02 Space/Context 页面可用性。两者可以按 owner 小范围交替配合，但不在一个业务文件里混写多个 owner。
3. D-03 API + D-04 AI 配置 UI；再 D-05 Conversations 页面完成真实用户对话链。同步执行 M-03/M-04，防止 IPC 契约与正式页面脱节。
4. D-06 GitHub 官方能力准备按连接器 owner 独立推进，不强制作为所有 UI 的前置；D-07 模块设置与权限界面接通。
5. D-08 多视图与布局恢复；D-09 安装与 Windows 综合验收。
6. 验收模式根据**现有实际完成情况**维护 B1/B2/B3 证据，不重做已成功的基础测试，也不能因 B3 部分成功就宣布 0.1.1 可交付。
