# WEX PC 0.1.1｜正式版本计划与三批施工任务

> 状态：用户已确认的版本范围与施工分批；任务完成状态须以最新 main 的源码和测试证据为准。制定日期：2026-11-02。
>
> 产品名称为 WEX；WEXPCeasy 是仓库名称。执行仓库：`owla19s-ux/WEXPCeasy`；默认集成分支：`main`。

## 1. 版本目标与边界

0.1.1 交付可安装、可启动、可交互、可持久化与恢复的 Windows AI 客户端及 Space / Context 基础宿主。以独立模块实现、跨模块业务闭环、桌面 UI 接线三批推进；不是完整 WEX 产品，也不是从零重写现有基础模块。

**0.1.1 范围**：Space / Context 基础管理与目录关联；Agent、角色与模型绑定；API Provider/Model/Key/参数/流式调用；Conversations 多轮会话、记录、基础编辑与重发；基础 Connections 配置与能力调用；Permissions 分层授权；配置/索引/日志持久化；App 模块生命周期；Electron/React 基础 UI、Windows 安装与数据恢复；同一 Context 的基础多视图和布局保存恢复。

**明确推迟至 0.1.2**：自由格子工作流及其可视化、正式调度器、DSH 插件系统产品化、DSH 连接器及外部 Agent 执行闭环。0.1.1 不得将这些能力设为交付依赖；只保留必要的模块公开接口和扩展边界。已有实验代码不视为正式产品实现。

**本版不做**：完整工作流编排、节点调度、DSH 真实联动、复杂个人定制工作台、未获批准的外部付费调用。安全敏感操作按现有权限政策及待决边界处理，不因进度默认放开。

## 2. 基线核对与施工方法

开始每个任务前：重新读取最新 main，按根 README → 当前模块 README → 源码/测试进入；本计划、AGENTS 兼容入口和历史契约仅在具体范围或规则问题时按需查阅；涉及具体功能编号、权限政策或跨模块冲突时，再定向查阅 docs/README.md、功能总表及相应决策；核对代码及测试，标记为已实现/部分实现/未实现/阻塞。历史 2026-11-02 快照已过时：截至 2026-11-06，Space 和 API 同样已有正式产品源码与测试，AI/roles、Conversations 和 GitHub/Local 具体连接器仍未见产品 src/tests。所有判断必须重新读取 main，不能以本句作为验收依据。Electron 宿主已有隔离实验但不等于 Windows 正式交付。不得用该快照替代施工时的实时核验。

按模块 owner 独立施工：一次完成合理范围的模块文件、公开接口、错误处理、持久化与测试；跨模块仅通过公开能力协作，不集中业务状态到 shared，不引入全局总管。单元与契约测试通过后再组合；UI 在基础链路可运行后接线。普通代码施工由工作模式提交代码、测试与回执，文档由普通对话模式核验后更新；用户明确授权的文档专项维护按授权范围执行。不再新增无明确阻塞依据的纯研究批次。

**GitHub 测试授权（2026-11-02 用户更新）**：仓库已公开，允许在 GitHub 上进行可用构建、测试和 GitHub Actions，**无需顾虑 Actions 额度**。根据实际 workflow 配置安排必要 CI，失败先定位根因并修复，不盲目重复运行；可用本地/云端测试仍可作为补充。没有真实 Windows 运行证据不得声称 E4 通过。每个任务回执记录实际 SHA、文件、测试命令、结果、未验证项与风险。

**持续施工要求**：在一次授权执行窗口内按完整模块或合理功能链路持续推进，包含实现、测试、修复与交付；不把单次工具调用、单个文件或一个提交视为任务完成，不要求用户反复发送“继续”。若出现真实权限、环境、安全或未决产品边界阻塞，记录证据后再请求裁决。正式操作方法与通用边界见仓库根 [AGENTS.md](../../../AGENTS.md)。

## 6. 批次管理与交付标准

- 三批共 24 个任务单元，任务编号固定为 B1-01～B3-08；按依赖推进，允许不冲突模块并行，不强制每项对应一个提交/PR。
- 每个任务必须明确 owner、实际实现文件、测试证据、完成/部分完成/阻塞状态和下一步；不使用虚构百分比。
- 默认 main 集成，只有真实并行冲突或高风险隔离时才使用短期分支；合并前核查冲突、测试、主线变化。
- 每批结束进行批次验收，上一批未完成的阻塞不得靠 UI 或文档掩盖；允许明确记录不阻塞版本目标的延期。
- 最终验收以真实产物、必要的单元/契约/集成/Windows 测试为依据，不把提交、PR、Actions 绿灯等同于产品完成。
