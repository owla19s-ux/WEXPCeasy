# WEX 功能总表细化与注释规范（Markdown V0.1）
日期：2026-11-01；状态：**编写规范与样本，尚非全域细化完成或版本冻结**。

## 目标与边界

现有 [F01–F15 总表](PRODUCT-FUNCTION-CATALOG-2026-11-01.md) 的 216 个 F 项保持**稳定索引**，不能因为重做详细解释而重排。总表已有 F/I/U/V/T 分层、A/B/C/D、各模块独立编号规则，本文件在此基础上补充“可见性、可操作性、文字注释、反例、证据和歧义控制”，**不建立第二份相互竞争的权威总表**。

用户当前只有手机，**本阶段以可阅读、可搜索、可引用的 Markdown 为交付**；Windows 操作 UI、真实 Provider 调用和桌面验收后置。不因 UI 未实现缩减底层能力。

## 1. 每条能力必须回答的内容

| 字段 | 要写什么 | 容易误判的地方 |
|---|---|---|
| F 功能索引、模块细分 ID | 保留既有 F 编号；详细能力采用模块已确定的独立编号，尚无编号时先写“细分候选”，不得自造正式编号 | 不把 F04-001-01 当作已批准编号 |
| 功能定义 | 一句话说明系统提供的行为与用户价值 | 不写“SDK 支持某 API”来充当产品功能 |
| 语义注释 | 对对象、调用资格、生命周期、配置覆盖、作用域与异常作自然语言解释 | 不只写标题/两个关键词，让施工 AI 自行脑补 |
| 能力触发者 | 用户、获准的 Agent、工作流、内部系统事件，可以多选 | 有 UI 按钮不代表只有 UI 能调用 |
| 用户可见性/可操作性 | 分别标注：能观察什么、能主动发起什么、哪些内部行为不可直接操作 | 一项功能往往含可操作的入口和不可操作的内部流程 |
| 输入/输出/权威 Owner | 输入字段类别、输出事实、数据由谁保存 | Provider SDK 不应拥有 Conversation、Operation |
| 依赖/前置/拒绝 | 授权、凭证、能力、运行环境，缺失后如何失败 | “可发现”不等于“可执行” |
| 不包含/禁止误读 | 明写不做什么，尤其是跨模块职责 | “取消本地流”不等于“远端计费取消” |
| 正/负/异常验收 | 最少各一个可执行观察结果，能区分代码行为与 UI 显示 | 有测试文件 ≠ 已通过测试 |
| 历史证据与状态 | 旧仓文档/代码/测试路径；A/B/C/D、实际代码状态、验证环境分别标 | 历史建议、旧 Android 实现不自动变成 PC 实现 |

### 可见性与操作性：不是三种互斥的模块

- **可见且可操作**：用户能配置/启动/取消，例如设置 API Connection。
- **可见但不可直接修改事实**：用户可以查看真实 usage、状态、错误，但不能把服务商账单直接改为已付。
- **内部不可直接操作**：SSE 拼帧、Continuation 校验、参数映射、脱敏、状态结算。
- **混合**：用户发起“停止”是交互，取消信号传播及远端状态仍属于内部能力；同一 F 项应记录两者，不强迫单选。

可见性是产品行为注释，**不替代**已有 F（基础能力）/I（交互语义）/U（UI 控件/布局）分层。不同入口（普通对话、Context、AI、工作流）可能引用同一基础功能，但各入口授权各自生效。

## 2. 标准 Markdown 条目模板

```md
### <既有 F 编号>｜<功能名>
- 细分 ID：<已批准模块编号或“候选，待模块 owner 分配”>
- 需求状态：A / B / C / D（复合按原表）
- 实现：未实现 / 原型 / 正式实现（注明仓库与路径）
- 验证：未验证 / 替身 / 真实服务 / Windows E4（注明证据）
- 可见/可操作：用户能看到……；能主动做……；内部自动……
- 触发者：用户 / Agent / 工作流 / 系统
- 定义与注释：……
- 输入 → 输出及 Owner：……
- 前置/依赖/拒绝：……
- 不包含：……
- 验收：正常……；拒绝……；异常……
- 历史依据：<可点击的原仓文件或提交>
- 待决歧义：……（无则写“无新增待决项”）
```

## 3. 细化、审查与治理顺序

1. 读取**当前** F 总表、功能—契约映射和模块 owner 契约，先建立行级可追溯索引。
2. 回查 APS/WEX/WEXPC 的详细研究及实现，只提取与当前目标仍相关的事实，显式记录旧产品政策冲突。
3. 补齐用户可见/可操作/内部行为、详细语义注释、负面边界、输入输出及验收。
4. 检查遗漏、重复、跨域 Owner 错位；存在冲突写“候选/待决”，**不得由 AI 自行把 B/D 升为 A**。
5. 模块详细规格写在模块就近 Markdown，产品总表仅链接和追踪，不复制另一份可冲突的状态数据。
6. 先以 F04 验证此写法；再覆盖 F01～F15。完成度必须是逐项计数，不能因建成模板就宣称 216 项详细规格完成。

**唯一功能清单与注释正文**：[F01–F15 产品基础功能总表](PRODUCT-FUNCTION-CATALOG-2026-11-01.md)。F01～F04 已原位合并详细注释，后续各域也必须在同一文件对应功能域内补充，不再生成单独注释表。

## 4. 完成判断

“详细功能规格完成”至少要求：原 F 项全覆盖；每条有可理解的定义、可见/操作/内部区别、Owner、依赖、拒绝、边界、验收、状态与来源；对未确认语义不伪造结论。**不要求在手机阶段做页面、安装 EXE 或运行真实模型**。
