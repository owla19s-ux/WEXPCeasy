## 0. 使用规则：空间结构与功能映射分离

**四个概念区域不等于四个永久占位的硬编码列；具体功能另由独立 UI 映射确定。** 本文负责列、面板、导航、布局与可用空间的组合规则；[0.1.1 UI 功能映射与设计收口](WEX-PC-0.1.1-UI功能映射与设计收口-2026-11-07.md)负责每个用户功能如何被发现、操作、判权、反馈和恢复。两者互补，不替代产品功能表、I 交互语义、正式版本计划或模块 owner 契约。

**以后每个 0.1.1 用户可操作功能都必须明确六件事**：
1. 入口在哪里（列、视图、设置、菜单或可信弹窗）；
2. 用户怎么操作（具体行为与业务意图）；
3. 调用哪个模块（唯一 owner 及公开接口/受控 app IPC）；
4. 权限怎么确认（可信主体、入口、目标、动作和范围）；
5. 结果在哪里显示（成功、失败、拒绝、取消、过期或未知）；
6. 失败如何恢复（保留输入、重读修订、追查原回执及安全重试）。

**约束施工 AI**：不得看到一个功能名就自行新增页面、模块、业务数据结构、对象实体或权限政策；UI 负责呈现和交互，不能把视图状态当作领域事实。功能缺乏真实公开能力时应明确不可用，不能假装已实现。

## 1. 定位与版本边界（2026-11-07 本轮收口）

本轮明确的是 **PC 基础 UI 结构与交互语义**，不是一次性落实全部未来工作台功能。旧版“始终显示独立第二、第三列”“第四列默认三段展开”“角色窗固定嵌入第一列”“底部为固定扩展区”的表达均以本版修订为准。

- ① 全局 Space / Context 导航；②＋③ 构成**一个完整的中间多视图工作窗口**；④ 右侧辅助窗**默认收起，具体辅助内容暂缓设计施工**。
- 中间工作窗口默认由当前视图占满：**没有选中需要独立打开的文件或对象时，第三列不占空白位置**。点击文件等对象后，在当前视图旁按需出现预览/编辑子窗，视图本体与结构导航保留；关闭子窗恢复完整工作空间。
- 第二列底部为**浏览器式视图标签栏**，首个默认视图为 **Context 配置/项目配置**，可切换源码目录、设计资料和其他获准视图。视图标签与文件预览/编辑标签不是同一种标签；是否固定/禁止移除默认 Context 标签尚未冻结。
- **主动切换布局**（单视图展开、两个完整视图并排、关联定位）与**默认点击对象**是不同操作；当前确定可扩展方向，不等于全量进入 0.1.1。
- 底部交互栏与虚拟形象是**彼此独立的 UI 对象**，可联动但不互相作为业务 owner；第四列、底部交互栏与虚拟形象均不应承担核心业务状态的权威职责。
- 不改变现有 Space/Context/Connections/Agent/Conversations/Permissions 等领域 owner、正式权限规则、公开接口契约和版本延期决定。

## 2. 基础结构（默认与按需展开）

```text
WEX 主窗口（默认：第四列收起、预览窗未打开）
┌──────────────────┬──────────────────────────────────────────────────┬─┐
│ ① Space 导航     │ ②＋③ 共享工作窗口：当前视图完整占满              │④│
│ 顶部类别：        │                                                  │收│
│ [个人][工作][公开]│   当前视图，例如 Context 配置 / 源码目录         │起│
│ Space → Group?    │   没有默认空白“第三列”                           │入│
│      → Context    │                                                  │口│
│ 普通对话入口      │                                                  │ │
│                  │ [Context 配置] [源码] [资料] [+] 视图标签栏       │ │
└──────────────────┴──────────────────────────────────────────────────┴─┘

打开当前视图里的文件/对象后（默认点击行为）
┌──────────────────┬─────────────────────────┬────────────────────────┬─┐
│ ① 导航           │ ② 当前视图结构/列表      │ ③ 按需预览/编辑子窗     │④│
│                  │ 保留目录及已选中项       │ 文件详情 / 编辑 / Diff  │收│
│                  │ [视图标签栏：底部]       │                        │起│
└──────────────────┴─────────────────────────┴────────────────────────┴─┘

主动请求双视图（未来布局扩展；不等同于文件预览）
┌──────────────────┬─────────────────────────┬────────────────────────┬─┐
│ ① 导航           │ 视图 A（如源码）         │ 视图 B（如功能表）      │④│
└──────────────────┴─────────────────────────┴────────────────────────┴─┘

独立层：可收起/展开/换方向的交互栏；独立自由悬浮虚拟形象。
交互栏收起时，工作页面可仅留下自由悬浮的虚拟形象。
```

- 以上不是四个永久并列的硬编码 React 面板。中间区域采用可调整的工作空间布局；默认完整视图与按需预览是当前基础设计。
- 第一列、右侧辅助窗和底部交互栏各自收起时，释放的空间回归中间工作窗口；虚拟形象属于悬浮层，不强占页面固定列或行。
- 视图切换应保留目录展开、选中和必要的编辑草稿状态；关闭视图标签不等于删除实际资源。
- 视图管理、文件预览和主窗口布局是三个不同层级的状态，不能混成一个路由跳转。

## 3. 第一列：Space 类别与 Context 导航

- 顶部“个人 / 工作 / 公开”是**横向并排的三个窄而高、呈竖栏形的类别按钮**，不是上下堆叠的三条横条；文字应正常横排可读，不因竖屏预览挤成不可读状态。它们是 Space **类别**，不等于 Space 或 Group。
- 下方按已有模型显示 Space → 可选 Group → Context；保留独立普通对话入口，不要求先创建 Context 才能对话。
- 第一列可从正常展开切换为图标窄栏或完全隐藏；完全隐藏后，中间工作窗口扩展到左边界。
- 用户管理类别、Space、Group、Context 时复用已有 Space owner 及权限/生命周期规则；不引入 Placement。
- **虚拟形象不属于第一列的内嵌内容**。其页面内悬浮层独立于第一列是否展开；设置入口必须可独立访问，不依赖形象可见性、播放状态或交互栏展开。
- 宽度、字体、折叠控制与 Space 列表布局以 PC 实测为准，不能因初期图示冻结绝对像素。

## 4. 第二列：浏览器式多视图标签与当前视图

**第二列并非始终独立占用固定宽度。** 它所代表的视图管理与当前视图导航处于 ②＋③ 共享工作窗口内，默认未打开对象时当前视图可以占满整个区域。

- 底部为当前 Context 的**浏览器式视图标签栏**：默认第一视图 **Context 配置/项目配置**，并可有源码目录、设计资料、会话、未来功能表/架构树等视图。当前可用视图以已批准的资源和已有能力为准；未来视图不要求立刻实现。
- Context 配置视图不可遗漏：其基本信息、稳定 Context ID、主地址、命名附加地址（名称/地址/备注）、关联工具/能力、Agent/角色等现有获准配置项目，应按模块实际能力呈现；不自行创建新配置语义。
- 用户可切换、添加、修改、移除、重排可管理的视图标签；标签过多时横向滚动，不自动换成多排。默认 Context 视图是否可移除、能否移动仍待讨论。
- 当前视图自身决定内容形态：源码视图是目录树/搜索/列表；设计资料视图是资源列表；Context 配置视图是配置导航与内容；对话视图是会话列表；未来功能表是功能节点/状态结构。**不能把所有视图都写成目录树。**
- 点击目录里的文件等对象，正常行为是保留当前视图及其导航状态，**在旁侧打开按需文件预览/编辑区**，不是替换整个工作窗口；点击另一个文件更新该预览。关闭预览恢复当前视图完整空间。
- 两个完整视图并排、跨视图关联定位/高亮、单视图最大化为未来应兼容的布局方向。功能表状态（如绿=验收通过）需来自真实 Verification/Acceptance 证据，不能由 UI 擅自推定代码完成。
- 标签页表示**显示与组织视图**，不是复制资源对象、隐式开权限或删除源文件。

## 5. 第三列：按需出现的预览/编辑子窗与文件同步

**第三列是动态内容区域，不是启动后永久显示的空编辑器。** 当用户在完整视图中打开具体对象时，布局在该视图旁分出预览/编辑子窗；当前视图保留。用户关闭预览后释放该区域。某些视图（如 Context 配置）本身也可在完整工作窗口内呈现表单，不要求每次操作都生成子窗。

- 可承载获准的文件查看/编辑/Diff、对象详情、完整 Conversation 或相应配置内容；由具体视图的交互规则决定打开方式，不把每一次选中都硬编码成窗口替换。
- 如有多文件预览/编辑标签，其标签只管理已打开对象，**不同于第二列底部的视图标签**。
- 默认“点击文件→预览/编辑”与用户主动“展开视图/双视图并排”必须区分，布局改变不得擅自保存、关闭或重新发起业务任务。
- 真实文件编辑仍使用 Local/GitHub、App/IPC、Permissions 正式边界；AI 或外部编辑器变更文件时，不能覆盖用户未保存草稿。
- 旧版已列的同步安全要求继续有效：只读内容收到变更提示后核对当前版本；未保存缓冲区显示磁盘版与草稿差异；写入请求使用版本/授权控制；超时/unknown 时核验回执；删除或失联明确显示；文件监听仅是变更线索而非事实权威。
- 编辑与权限、数据来源、冲突保护、真实状态反馈必须由已实现的 owner 能力接线，不因预览 UI 存在而宣称保存/验收能力完成。

## 6. 第四列：默认收起的辅助区域（具体内容暂缓）

- **默认收起**，仅保留可发现的右侧展开入口；不占常驻完整列宽，中间工作窗口获得空余空间。
- 当前先明确辅助容器的布局边界，**不做默认三段窗口，不预先指定上 Context、中执行记录、下 AI 对话**，也不为了第四列新增假数据和业务面板。
- 未来可容纳 Context/对象摘要、执行/回执、辅助对话等，但功能优先级、切换方式、展开形态须在主工作区交互稳定后另行评审。
- 用户正常完成 Context 配置、源码导航、文件预览编辑和对话，不应依赖第四列打开。
- 展开/收起不得丢失主工作区草稿，不能改变业务授权或停止既有执行。

## 7. 辅助对话：后续场景约束（非第四列当前施工要求）

独立普通对话与 Context 相关会话遵守原 Conversations owner 与已有 UI/IPC 接口。未来若在第四列增加辅助对话，也不能复制 Conversation、静默切换会话、重发请求或因收起面板丢弃未保存草稿。

对话发送、流式响应、停止、附件、`@` 引用、模型/Agent 选择等属于已有独立的对话与功能映射要求，不以第四列提前存在作为实现前提。语音及其 Provider 深度按正式版本与技术验证决定，不由辅助窗草案擅自扩范围。

## 7.4 PC 设置页面：左侧两级导航、右侧详细配置（已确认）

- **充分利用 PC 页面横向宽度**：打开设置后，在主操作区域显示**左侧导航 / 右侧详情**。左侧按“大类 → 小类”展开和选择，右侧显示所选小类的完整设置、添加、编辑、连接测试和错误提示。左侧与右侧**各自纵向滚动**；右侧滚动不带着左侧导航移动。无需沿用 Android 的整页上下折叠手风琴。
- 一级大类**继承原 WEX 已确认的四组**：**连接与服务 / 权限 / 验证 / 系统**，而非历史八组并列一级菜单。左侧点击大类展开/收起小类，点击小类在右侧切换详情；右侧表单较长时可继续纵向滚动。
- **连接与服务**小类候选：API/Provider/模型、Agent/角色配置、GitHub、Local/工具与连接状态；**权限**：模块启用、全局访问、对话/具体操作授权；**验证**：可用性检查、实际连接测试与诊断（不冒充 Task Verification）；**系统**：程序与数据目录、工具环境目录、界面/角色展示、日志/故障诊断、版本/运行状态。小类只展示已获批准且具备真实配置能力的项，不为分类而新建业务模块。
- 每个设置小类的专属表单、配置权威和校验仍归原 owner，`UI/settings` 只提供导航/面板挂载；复杂字段可在右侧详情内部按组折叠，不需要强制新开独立 Windows 窗口。
- API Key 必须走受信录入，不进入可回读的 Renderer 状态；真实连接测试区分“配置保存”和“实际联网测试”。审批展示可信主体、入口、动作、目标与范围；第四列可展示待决提醒，但最终由 app 可信入口和 permissions 确认。
- 设置入口必须独立可达，不依赖第一列、虚拟形象或交互栏是否展开；快捷键系统未来统一在设置中管理。

### 7.4.1 主内容与窗口切换的最小行为

- **第一列**切换 Space/Context 与独立对话入口；**中间共享工作窗口**由底部视图标签切换 Context 视图，点击对象按需出现预览/编辑区；**第四列**默认收起，具体辅助内容后议。
- 切换标签只改变当前展示，不创建新的 Context 或 Conversation、不取消正在生成的 AI 回复；关闭标签只关闭对应视图，不等于删除对象、关闭会话、撤销操作或停止外部任务。
- 按需预览/编辑子窗保持合理的未保存输入保护和原视图回返；切换 Context 后不得把旧异步响应写入新对象。多 Windows 顶层窗口的组织策略与任意拖拽分屏仍属后续研究，不在 0.1.1 预造窗口体系。
- 设置可由第一列进入，返回主工作时恢复先前可用的工作焦点/标签；精确标签上限、默认打开策略等属于试排/实现选择，不得据此制造新业务对象。

## 7.5 状态反馈与失败恢复的跨列原则

- 操作发生处就近显示反馈；当前第四列默认收起且具体内容未定，不得强制把 Connections Operation/执行记录放在第四列。可由当前视图、受控详情入口或系统诊断呈现，未来第四列辅助展示须另行设计。
- **确认提交、明确未提交、取消、拒绝、结果未知必须区别表达**；提交未知保留原 intent/Operation，提供查询/回读入口，不能默认再次发起具有副作用的请求。
- 来源失联、撤权、过期、部分读取和版本冲突有对应空态/警示；保护输入草稿，防止旧异步响应污染已切换的 Context/Conversation。
- 现阶段 Workflows 尚未正式提供的任务/核验状态不可在第四列伪造“运行成功/验收通过”。

## 8. 独立交互栏 × 独立虚拟形象（本轮明确）

### 8.1 定位
- **交互栏**与**虚拟形象**是两个独立 UI 对象，不互相作为实现容器或数据 owner；它们可以共享展开/关联状态，但不能将形象写死成栏内的固定按钮。
- 底部交互栏借鉴 Windows 任务栏：是可组合的交互对象入口（如 AI、秘书、Context 或获准对象），可请求中间工作区打开对应内容，但与第二列底部的**视图标签栏**完全不同。
- 虚拟形象是可独立悬浮、拖动、展示静态图片或 GIF 的交互入口；不是装饰性第一列头像，更不是默认点击就恢复主工作窗口的桌面图标。

### 8.2 WEX 主窗口内部联动规则（基础交互）
1. 交互栏收起时，**仅虚拟形象可以保留在工作页面的自由悬浮层**，可在允许的窗口范围内拖动；不因为导航或辅助窗收起而消失。
2. 点击自由悬浮形象可**展开交互栏**，形象按保存的交互栏内相对位置回位；再次收起时返回此前自由悬浮位置。
3. 交互栏展开时，虚拟形象可**在交互栏范围内连续拖动**，不是左/中/右三个离散位置。应区分拖动和点击，避免拖动误触展开/收起。
4. 至少区分保存**窗口内自由悬浮位置**与**栏内相对位置**两套状态；栏的方向改变后通过相对坐标定位，确保窗口缩放、重启和 DPI 变化时可恢复到可见范围。
5. 交互栏默认在底部，未来需要兼容顶部、左侧、右侧及不同展开形态；**本轮不冻结各方向全部具体布局，也不强制把未来方向一次开发完**。
6. 交互栏是否展开不应导致业务任务取消、Conversation 重建或第二列视图切换。两者均不能借联动直接提升权限。

### 8.3 Windows 桌面级悬浮（单独研究，非 0.1.1 当前实现）
主工作窗口最小化后，未来可能由独立系统级透明悬浮窗继续显示虚拟形象。**此模式必须单独设计**：点击行为不默认恢复完整 WEX 主工作页面；桌面小交互、窗口焦点、置顶、多屏、可见性等以后讨论。页面内悬浮不等同于 Electron 顶层悬浮窗口，不能用一个 React fixed 节点假装满足桌面行为。

### 8.4 与工作区的布局边界
交互栏默认收起不强占主工作区高度；展开时遵守用户定义的空间模式。虚拟形象属于独立悬浮层；导航/交互栏都隐藏时中间工作区能延伸至左边和下边，除形象浮层外没有预留的空白区域。

## 9. Context 地址、资料和界面映射

- 复用 Context 既有主地址及多个附加地址（名称、地址、备注）；这些地址可以对应本地目录、GitHub 主仓、参考文档、产出地址等，不能强行合并为唯一工作目录。
- 用户选择其中一个目录，在 Context 多视图中添加“设计资料”，即可浏览/编辑资料。**不要求现在建设独立资料管理系统**。
- 设计/研究草案与源码施工资料逻辑分离；以 WEXPCeasy 现有源码/模块文档为参考，但不强制把探索性设计资料放入源码目录。
- 用户可以直接编辑资料；AI 可提出更新建议并在有效授权下写入。未经确认的猜测不得无标注地写成正式设计；文件不是聊天的自动副本。
- 视图只是某目录/对象的呈现，移除视图不得移动或删除真实资源。

## 10. 持久化、异常与可用性

建议保存并恢复：第一列显示/折叠状态、中间工作窗口布局、当前 Space/Context、视图标签/顺序/当前选中、目录展开/选中、按需预览的打开状态及编辑草稿、独立交互栏展开与布局状态、虚拟形象自由悬浮位置与栏内相对位置。第四列具体面板结构待后续设计；持久化不得代替业务 owner 与授权回读。

异常覆盖：
- 重启后资源失联、地址变化、撤权；
- 变更事件丢失、异步回执迟到、重复通知；
- 用户草稿与 AI/外部写入冲突；
- 多列缩到极窄、窗口 DPI/分辨率变化；
- 关闭/切换对话但生成仍进行；
- 语音设备不可用、上传/引用失败、Context 引用无读取许可；
- 视图所引用的工作流数据不存在时只显示空态，不假报状态。

## 10.1 Windows 安装、目录选择与崩溃后外部排查（历史要求回收）

参考既有[源码与 Windows 数据存放要求](../architecture/SOURCE-LAYOUT-AND-WINDOWS-DATA-2026-10-30.md)、[Windows 生命周期研究](../research/WINDOWS-LIFECYCLE-2026-10-31.md)。这不是新增 0.1.1 模块。

- **不做欢迎教程/功能介绍式首次引导**。正常安装后直接进入主界面；**必要的安装目录与数据根选择/验证不能省**，目录不存在、无权、已占用、格式不兼容时只展示最小必要选择/修复入口。
- **程序安装目录**：用户在安装 EXE 时选择；主程序/发行依赖/内置资源可独立定位，程序升级或卸载不能默认清空用户资料。
- **WEX 公共用户数据根**：独立于安装目录，由用户选择或接回已有目录；保存公共配置、索引、应用必要状态、技术日志和可控缓存等，不强制容纳所有 Context/Space 的实际资料。
- **工具与开发环境目录**：作为与安装、公共数据、Space 实物分开的**用户可配置工具资源位置**，在设置→系统中显示、选择和检查；可以关联既有编译器、SDK、工具链/外部工具，不强制首启配置、不默认下载工具，不将其等同插件机制或新增业务 owner。具体环境安装/迁移机制依 tools/Local 正式范围核定。
- **Space 工作区 / 独立 Context / 其他外部资源**：用户按实际位置单独选择或关联；源码仓库、资料、产物可位于其他盘符与路径；添加引用不自动迁移、复制或赋权。
- **尽量少写 C 盘**：受控缓存、日志、Chromium profile/session、可控临时文件应按验证过的路径策略优先进入选定数据根；不能承诺系统盘零写入。必须审核 Electron `userData`、`sessionData` 在启动早期的时序与实际安装器/更新缓存位置，Windows 凭证/系统注册项等必要例外可追踪。
- **崩溃/无法启动时不依赖 WEX UI 才能排查**：让用户或外部维护工具能够从已知的安装、数据和工具环境位置找到**实际安装文件、版本/模块信息、日志、崩溃诊断及必要数据路径说明**；不因主程序崩溃丢失唯一索引。支持脱敏日志/诊断的离线定位与读取，避免将 Key/Token 泄露到普通文件。
- **“可查安装文件”不等于可直接改产品源码**：Electron 的 ASAR/打包构建不保证保留原始 TS/React 源码；如要崩溃现场直接检查可读源码/源码映射，需独立确定发行包的诊断素材或开发版方案。0.1.1 不据此承诺可热改源码或自动重建。
- **重装/恢复**：公共根内有可识别的非秘密定位/格式信息，重装系统后可重新选择原根、重连外部目录；正常重启与重装的凭证/权限规则不同，**重装不能自动恢复旧有效授权或凭证绑定**；旧 Operation 结果未知时不能自动重复操作。
- **安装器/Windows E4 验收**：实际选盘、独立用户数据根、少量系统盘例外清单、目录权限、中文路径、失联/占用、崩溃后的离线诊断定位、卸载留数据和重装接回均须真实验证，不能只凭“EXE 能启动”宣布通过。

## 11. 与仓库分工及实施安排

- `UI/`：四列容器、视图装载、状态展示、辅助窗口、布局交互；不负责实现文件系统、权限、聊天或任务业务。
- `views/`：视图配置/映射等既定职责；UI 不另建同一份业务事实。
- `space/`：Space 类别、Space、Group、Context、地址关联权威规则。
- `conversations/`：Conversation、消息与生成事实；UI 只呈现、编辑入口与当前选择。
- `connections/api`、`connections/local`、`connections/github`：各自协议/能力和资源操作；`connections` 维护通用 Operation；`permissions` 负责有效授权；`app` 提供受控桌面 IPC 和平台能力。
- **工程时序**：本文件属于 B3 UI 细化设计输入，不视为 B1/B2 已完成证据。施工前以最新 main、正式 B3 任务、模块 README、真实代码和测试为准；没有明确接口支持时先留下界面能力的不可用状态，不能用假的成功结果冒充功能闭环。

## 12. 初步验收清单（待纳入正式 B3 任务时逐项核对）

1. Space 类别以纵向按钮切换；用户自定义类别；Group 与 Space 类别不混淆。
2. Context 默认打开配置视图；可添加/切换获准源码、设计资料等标签，切换不删除资源。默认视图占满中间区域。
3. 拖动三条竖向分隔线、第四列横向分隔线，重启恢复合理尺寸。
4. 第三列只读打开的文件被获准 AI 修改后出现更新反馈和最新内容；可看差异。
5. 第三列有本地未保存编辑时，AI/外部修改不能静默覆盖草稿。
6. 真实文件状态与 AI 操作回执失败/未知分别呈现。
7. 文件颜色标记有状态维度、文字、来源，不能把 Git 修改等同验收。
8. 第四列默认收起；仅验证展开入口和主窗口空间释放，不验收尚未设计的辅助面板。
9. 第四列对话展开占满该列，再收回原布局；消息和草稿不断裂。
10. 主对话和文件对话用标题+地址区分，仍靠稳定 Conversation ID 恢复历史。
11. 对话输入支持 `+` 附件入口和 `@` 引用目标选择，发送时验证来源和授权。
12. 语音输入入口及不可用/失败状态清晰；真实语音实现深度单独验收，不以按钮存在视为语音可用。
13. 独立交互栏可展开/收起；虚拟形象与交互栏联动时不删除 Conversation、不停止任务。
14. Windows 窄窗口、高清缩放、重启、失联、撤权、编辑冲突、异步变更至少有明确可复现反馈。
15. 设置入口独立可用；虚拟形象属于独立页面悬浮层，不作为第一列内嵌头像；媒体功能深度按已批准施工范围核验。
16. 第一列折叠/隐藏时虚拟形象仍可在主窗口内自由悬浮，不强占第二列底角或遮挡视图标签；交互栏收起后点击形象可重新展开。
17. 不创建 Context 也能进入普通对话；对话视图和按需打开的内容区显示同一 Conversation，迟到的异步结果不得污染新会话。
18. 第三列可在文件、Context 详情、模块配置和完整对话之间切换；不复制各模块业务事实，不以假表单宣称底层可用。
19. API/Agent/权限/Connections 从设置或明确对象入口到达，能操作/拒绝/显示原因；授权 UI 明示真实范围且不会因对象选择自动授予权限。
20. 首次数据根选择与重启接回显示实际状态；失败/未知保留原关联及草稿，不自动重复高风险写入。

## 14. 中间工作窗口标签、预览与状态管理细化（2026-11-07；自主实现设计 V1.0）

> 本节是基础 UI 交互方案，不自动批准新的 views/Space/文件领域 schema，也不要求 0.1.1 实现完整双视图/任意停靠系统。若历史试排与本节冲突，以 §§1–8、§14 及 §15 中明确已确认的原则为准。

### 14.1 独立职责与归属

- **浏览器式视图标签栏**位于中间工作窗口底部。一个 Context 有一组视图；首个默认入口为 **Context 配置/项目配置**，内容由真实 Space/Context 能力提供。是否永久固定、是否允许关闭/调整位置**未最终确认**，施工时不得把候选限制固化为不可变产品政策。
- 标签用于切换**工作视图**（Context 配置、源码、设计资料、会话、后续功能表/架构树），不等于文件预览/编辑标签，更不等于独立交互栏的 AI/对象入口。
- **视图内容容器**：未打开需单独查看的对象时，占满 ②＋③ 共享区域，无第三列空白占位。
- **按需预览/编辑子窗**：点击可打开对象时，在当前视图旁出现，原视图结构、选择、展开和滚动状态保留；关闭预览恢复视图的完整宽度。
- **布局控制**只决定内容区域大小与显示组合；不拥有文件、Context、Conversation、Verification、权限或执行事实。UI 与底层连接必须通过已有公开端口及受控 App/IPC。

### 14.2 标签操作

| 用户动作 | UI 行为 | 业务安全边界 |
| --- | --- | --- |
| 添加 `+` | 从当前 Context 可用且有权限的视图类型、资源引用中选择创建/添加显示入口 | 不自动复制文件、不新增其他领域对象、不得扩大引用授权 |
| 单击 | 激活视图并恢复其可用导航和预览状态 | 不触发自动写入/任务派发 |
| 编辑显示名 | 修改标签展示名称或该视图已获准的显示配置 | 不重命名物理文件夹、Space、Context 或资源 |
| 拖动左右排序 | 单行标签栏内调换次序、更新视图顺序 | 不改变底层数据目录及执行顺序 |
| 关闭普通视图标签 | 移除显示入口；有未保存编辑则先保护/询问 | 不删除真实文件、地址、Conversation 或 Context |
| 标签过多 | 单行横向滚动并保持当前标签可见；保留 `+` 入口 | 不自动多行挤压工作区 |
| 切换 Context | 载入目标 Context 的视图集合与焦点，原 Context 状态按权限/配置可恢复 | 旧请求的迟到结果不得污染目标 Context |

设计不强行规定同一种资源视图是否支持多实例；首先需要稳定区分 **视图实例 ID** 与 **引用目标身份**。默认 Context 配置视图的移动/关闭策略待 UI 实测与用户确认。

### 14.3 四层独立 UI 状态

1. **Context 视图集合状态**：Context ID、视图实例 ID/类型、关联目标引用、标签顺序、激活视图 ID。
2. **单视图临时状态**：目录展开、筛选、选中目标、滚动与焦点；切走后返回可恢复，不必让全部离屏组件持续运行。
3. **预览/编辑会话状态**：目标稳定身份（连接器/范围/地址/修订等）、临时预览槽、已固定打开对象、编辑草稿和冲突标记；不能只用文件名当身份。
4. **显示布局状态**：默认完整视图、按需预览/编辑、分隔比例，以及未来主动双完整视图；布局变化不触发业务修改。

**临时预览**：单击文件优先复用一个临时预览槽；打开其他文件时，只可替换无未保存变更且不被固定保留的预览。**固定打开**：双击或主动固定使对象保留为独立打开的编辑/详情会话；开始编辑也不能让草稿被后续预览覆盖。关闭未保存编辑必须阻止静默丢失，并提供明确的保存/放弃/取消路径（实际保存需有效权限及 owner 确认）。

**按视图分别保存可恢复的预览选择**，切回源码/资料等视图时可恢复先前对象。保留状态不代表缓存内容永久有效：重新显示必须验证当前访问权限、对象是否仍存在及真实修订；撤权或失联显示受控空态。普通 UI 布局/引用 metadata 可适度持久化，**敏感文件内容及未保存草稿不能未经安全设计直接塞入 localStorage**。

### 14.4 布局与生命周期开关

```text
选中视图 ── 默认 ──> [完整视图占满共享工作窗口]
                         │ 单击文件/对象
                         ▼
                   [视图 + 预览]
                         │ 开始编辑/固定打开
                         ▼
                   [视图 + 受保护编辑]
                         │ 关闭预览（无未保存草稿）
                         ▼
                   [完整视图恢复]

用户主动双完整视图 ──> [视图 A | 视图 B]（未来扩展，非文件预览替代品）
```

- 默认对象点击并不替换当前视图，不应误入主窗口全屏路由；主动双视图并排、单视图展开是额外布局命令。
- 中间分隔可拖动、支持键盘可访问操作与最小可用宽度；主窗口缩窄时需保证关闭/恢复预览的入口始终可操作。
- 保存布局前后区分可再计算的显示尺寸与稳定视图选择。旧 `wex.workbench.layout.v1` 是**永久四列**布局格式，不能直接套用成新共享窗口状态；应迁移或安全回退，不污染业务数据。
- 预览关闭不能删除文件、Context/Conversation 或中断后台操作；正在执行的外部操作归原 owner 管理。

### 14.5 自主实现原则及最小 UI 构件

**WEX 自己编写**视图标签管理、显示布局、文件预览生命周期及交互状态协调；参考浏览器/IDE 的交互行为，但未经用户批准不得复制第三方工作台源码或引入完整 Docking/窗口管理框架。React、Electron、TypeScript、CSS Grid/Flex、浏览器原生 Pointer/Keyboard/ResizeObserver 等基础技术照常可用。

候选 UI 职责：中间工作窗口容器 / 视图标签栏 / 当前视图挂载 / 按需预览-编辑宿主 / UI 状态及迁移。**只是实现职责，不要求预先建立五套新业务模块或新的 domain schema。**

### 14.6 最小可验场景（不等于本轮已实现）

1. 进入 Context：默认 Context 配置视图，占满共享工作窗口；没有第三列空编辑器。
2. 切到源码视图，点文件：右侧预览出现，原目录展开与选中保持；继续点别的文件复用无草稿的临时槽。
3. 固定/编辑文件后继续点别的文件：旧草稿不被覆盖；可返回原对象。
4. 关闭预览：视图恢复完整空间；关闭标签不删除实际资源。
5. 切源码→设计资料→源码：恢复有效视图位置和预览选择；权限撤销/来源失联不得显示旧敏感内容。
6. 不同 Context 含同名文件：身份隔离；旧 Context 异步回包不能污染新 Context。
7. 标签添加、改名、关闭、左右排序、横向滚动和重启恢复；非法或旧版持久化布局安全降级。
8. 分栏拖拽/键盘调整与窗口缩放不遮挡控制；未保存编辑期间关闭/切换有明确保护。


## 15. Windows 原生窗口、自适应与分隔线验收补充（2026-11-07）

### 15.1 窗口层与应用内部布局分工

- **优先保留 Windows/Electron 原生有边框窗口**，使用系统标题栏提供最小化、最大化/还原、关闭，支持标题栏移动、边角缩放、任务栏/Alt+Tab、Windows Snap（如 Win+方向键、Win+Z）。不为追求外观在 0.1.1 改用无边框窗口重造系统按钮及吸附逻辑。Windows Snap 可用性须在真实 Windows 版本上验证。
- **最大化不等于独占式全屏**；窗口可以最大化、还原、最小化、左右半屏/四分屏、手动改变大小，WEX 主工作区必须适应实际剩余客户区尺寸。
- 原生操作系统负责顶层窗口移动/尺寸与吸附；**WEX 自主实现内部**第一列、中间视图、按需预览/编辑、第四列及以后辅助面板的布局与拖动，不复制第三方完整 Docking/工作台源码。
- 主窗口最小化时不擅自开启桌面级虚拟形象悬浮；那是独立未来设计，点击不默认恢复主窗口。

### 15.2 适配不是整体缩放

| 场景 | UI 约束 |
| --- | --- |
| 窗口从最大化变成普通尺寸 | 由窗口客户区尺寸重新计算可用布局，不清空标签/文件/编辑草稿 |
| Windows Snap 半屏、四分屏、小分辨率 | 优先收起第四列、收窄/隐藏第一列；必要时将文件预览临时改为单内容切换，不强行保留不可用的双栏 |
| 100% / 125% / 150% / 200% 显示缩放 | 以 CSS 逻辑像素及真实客户区测量；避免物理像素与 CSS 像素混用导致分隔线/悬浮层偏移 |
| Windows 仅放大文字 / 增大应用缩放 | 控件高度可增长、文字可换行或截断配 tooltip；输入/审批/保存按钮不被压出可见区；单独实测 Windows 文本放大对 Electron/React 的真实影响 |
| 双屏不同缩放与拔掉副屏 | 位置/尺寸恢复须约束到当前可用屏幕工作区，保证标题栏/恢复入口可找到 |
| 弹窗、下拉、右键菜单、悬浮形象 | 根据视口边缘重新定位；不盖住必要输入/保存操作，拖动和点击互不误触 |

不冻结固定响应断点；阈值应根据真实内容的**最小可操作宽度**和实机 DPI/文字大小确定，不能用一个永久的 `min-width` 伪造窄窗口支持。可用空间不足时，采用降级显示/内部滚动，不允许核心控制被裁切且无法访问。

### 15.3 分隔线拖动必须保留

- 第一列/中间窗口之间：调整导航宽度；第一列可图标化或完全隐藏。
- **仅在文件预览/编辑区出现时**，显示当前视图与预览之间的可拖动分隔线；默认完整视图时没有空白第三列，也没有幽灵分隔线。
- 第四列将来展开时，中间/辅助区之间允许调宽；未来双完整视图、辅助区内部上下分割可复用机制，但不要求当前施工全部完成。
- 继续复用既有 Pointer Events、键盘方向键、尺寸分配/恢复思路；支持拖动限制、最小可用宽度、取消拖动恢复、**双击恢复默认分割比例（设计建议，需实际验证）**，禁止将面板压到无法关闭。
- **用户布局偏好**与**依据当前窗口大小计算出的临时呈现结果**分离。Snap 缩窄时可临时单内容显示，恢复宽屏后尽量回到原分栏比例；实时缩放不得不停覆盖用户保存的比例。

### 15.4 UI 状态与窗口生命周期

- 最小化、隐藏、恢复、关闭、退出、后台执行是不同状态：不能通过 React 卸载猜测外部任务已取消；关闭确认沿用 App/Permissions 正式策略，不擅自增加后台默认授权。
- Tab/Enter/Escape、编辑器复制粘贴撤销、控件焦点恢复和分隔线键盘调整要可用；避免抢占系统/输入法常用组合键。状态标记要有文字/图标与来源，不能仅靠颜色。
- 视图、预览、菜单、对话和设置区保持各自滚动上下文；弹窗聚焦/关闭后焦点回到合适对象；迟到的旧 Context/文件请求不得覆盖新选择。
- 布局持久化不等于敏感编辑草稿可直接保存到 `localStorage`。升级既有 `wex.workbench.layout.v1` 需明确安全迁移/回退；在狭窄客户区恢复旧布局不可强行溢出。

### 15.5 现有代码静态核对（待施工、不是实机验收）

- `app/src/desktop-runtime.ts`：当前 `BrowserWindow` 为有边框默认样式，尺寸约 `1440×900`、最小 `1024×640`，默认启动调用 `maximize()`。原生系统标题栏可继续用；最小宽度有可能阻碍窄窗口与 Windows Snap，必须 Windows 实机验证再调。
- `UI/src/workbench.css`：`.workbench-grid{min-width:1006px}`，加上四列最小宽度会导致窄窗口溢出风险；不能只改 CSS 而忽略对应尺寸算法。
- `UI/src/layout.ts`：旧 `Layout.version=1` 永久四列、默认第四列 25% 且三个辅助面板；`fit()` 在可用宽度不足时仍保留硬最小列宽，与新默认完整视图不符。重构时要修改**旧保护型测试**，并增加窄窗口/布局迁移反例。
- `UI/src/workbench.tsx`：已使用 `ResizeObserver`、拖动分隔线和保存状态，可优先复用；当前未提供新版动态共享工作窗口。
- `UI/src/space.tsx`：异步 Context 打开/快速切换需要验证乱序回包隔离，避免 A 的迟到详情覆盖已切换的 B。
- 此处均为静态观察，不能替代 Windows Snap、不同 DPI/文字大小及真实窗口操作的实机回执。
