## 3. 提供/消费关系与依赖方向

以下是能力依赖，不是完整源码import许可表。提供方维护语义，消费者依窄端口；app注入实现。源码边、运行能力边、装配边分别检查，双向观察不强迫双向import。

| 提供方→消费者 | 必需能力/证据 | 方向与禁止绕行 |
|---|---|---|
| shared→各域/app | 提交成功/未提交/未知、权威修订回读、限定路径/秘密可用性 | shared不import领域实现，不自行解释Task/授权 |
| permissions→各正式入口与connections | 当前主体/入口/动作/资源决定和依据，非允许不得动作 | 事实宿主核验注入，permissions不反查所有领域私有库 |
| space→UI/views/对话/工作域 | 获准Context/组合引用、本体/关系修订和定位 | 外部文件版本另由实际资源owner提供，不把关联变授权 |
| AI→对话/工作域/选择投影 | 配置职责及本次不可变依据，当前获权历史解释 | 新工作准入与历史解释分开，不读“最新”覆写旧轮次 |
| connections→AI/对话/工作域/诊断 | 能力元数据、受控Operation、尝试观察/控制差异 | 消费者不解析厂商协议，connections不写Task或消息权威 |
| workflows→对话/UI/views/modes | 显式任务创建、定义/Task/核验投影和受控编辑 | 一般对话不必创建Task，视图不倒写任务 |
| workflows/runtime→connections（宿主注入） | 无Task也可用的资源协调依据/修订、未决占用和释放证据 | connections不能私有import runtime；预检与派发复核复用同一意图/协调引用 |
| 对应领域→connections回调（宿主注入） | 本次目标最小查询/写操作及领域修订规则 | 外部身份/范围每次核验，不给全Context/数据库 |
| 通用域→modes | 专业组合需要的通用创建/查询/编辑 | 源码依赖是modes消费通用出口；通用域不反依赖具体模式 |
| modes/领域→views | 专业规则身份/获准对象关系和来源版本 | views经注入消费；modes不导入views实现决定业务 |
| 领域窄桥→UI | 获准查询、意图提交、原关联恢复与状态证据 | renderer不导入Node/凭证实现；面板位置不改变业务owner |

装配根可以引用公开业务面和宿主专用装配面，不能以装配名义任意深导入private。运行回调端口可由消费者声明所需形状，但不能削弱提供方授权/版本前提。完整自动检查规则及例外管理见[tools施工规格](../tools/README.md)。

## 4. 四组优先边界审查结论

| 边界 | 责任收敛及重要失败例 | 相关契约 |
|---|---|---|
| Space↔Permissions↔AI | Space写选择、AI写职责、permissions写许可；解除关联/撤任不隐式删目标或撤权，后续资格仍按当前事实重判。入口B不能用入口A对同Context的许可；重装旧许可不复活 | SPC/AIC/PER行为样例；非对话入口映射D |
| Conversations↔Connections | 消息/逻辑生成与Operation/Provider分开；已落盘输入、外部接受、流式暂态、定稿保存分开观察。G1迟到不覆盖G2；重发是新生成，不重放未知工具 | 对话公开表+C01–C05；提交ACK丢失只读回、不再调模型 |
| Workflows↔Connections↔Permissions | 分配/准备不执行，连接宿主准入/保存attempt/适配；工作域按证据核验验收。runtime预检与最终准入绑定同一协调引用；Task与无Task同资源均受阻。所有非明确允许均零动作 | W01–W07+C02–C05+PER；unknown不释放占用、不盲重试 |
| Workflows/modes↔Views | 执行定义/依赖属工作域，专业对象关系属模式/原域，出现映射/布局属views；图上同名不等同机制。草稿不覆写运行结果，不直接采用ReactFlow Draft | W01/W07、modes与views；模式单向消费通用域 |

以上收敛没有新增全局状态管理器/协议总线/插件框架。四组的样例为设计验收要求，不是本轮已运行结果。原型证据只限定历史已测范围，未把参考函数提升为正式接口。

## 5. 接口、协议与独立验收

[app/COMMUNICATION.md](../app/COMMUNICATION.md)区分同进程、renderer/Node、独立插件、外部Agent和文件/Git/远端服务；维护可信身份、请求/意图/attempt关联、错误、能力协商和恢复边界。内部重构、兼容扩展、破坏语义与wire/data分别判断：TS仍兼容但默认权限/unknown/取消/重试变了，仍可能破坏。

每模块未来交付证据分四层：真实本域行为；公开能力的提供方/消费者/替身一致样例；真实装配与相关外部适配；最后L01–L12及故障场景的系统组合。模块通过不等于组合通过；缺真实提供方时明确限制，不用用户反复“继续”驱动碎片施工。

## 8. 后续专项：复杂交错操作链路压力测试（2026-10-31 需求记录；尚未执行）

**缘由**：L01–L12 是常规用户行为与基础异常覆盖，不能证明多个 Context、模块、执行者、窗口、安装代次、外部服务及数据盘在并发/断联/恢复条件下仍维持正确契约。第四批交叉审查还发现：普通领域提交与外部副作用不应机械共用同一去重机制；非对话入口第三层授权待确定；workflows↔connections 在持久派发/关联之间存在崩溃窗口；app/shared/permissions 的重装信任事实需明确唯一来源；模块能力应按成熟度分级。

### 覆盖审查：现有场景与真实使用的距离

截至本次审查，L01–L12覆盖基本业务语义，H01–H13加强并发/异常、DSH插件与连接墙；本次补入H14–H20以补足**无Task日常聊天、完整GitHub协作、首次装机环境诊断、人工接管、连接/能力演进、长期容量维护、Windows用户交互**。这不是宣称所有未来业务都已覆盖；长期账号/云同步、公共策略库、社交/市场、移动端协同仍属未来候选，不能因测试目录而自动扩入当前版本。

**与实机差异最大的测试类别：**
- DSH Core+Loader Linux hello插件加载 ≠ 用户安装目录中的第三方DSH Bundle在Windows/Electron宿主成功运行；还缺Service依赖、隔离、配置升级与卸载的实机证据。
- DSH协议替身与真实MISSING_CREDENTIAL失败 ≠ 真模型成功修改指定目录、会话恢复、进程树停止、产物可归因；成功验收需对照文件/Git实际变化。
- dependency-cruiser两模块夹具 ≠ WEX全仓源码模块依赖门禁；当前多数模块只有Markdown，无可检查的真实模块图。
- ReactFlow四节点/jsdom/HTTP ≠ Windows桌面真实鼠标/拖放/多图规模和Electron IPC安全。
- 12条样本与复杂场景文字推演 ≠ 持久化崩溃注入、权限竞态、远端GitHub副作用、重装及系统休眠的运行验证。
- 文档所称的成功/未知、CAS、身份代次等是未来提供方须兑现的业务语义，尚无真实驱动/故障注入结果；不能把“理论可以恢复”视作“能够恢复”。

**执行分级**：E0 文档责任/状态推演；E1 已实现模块的双方行为/故障替身；E2 本地真实进程+文件/数据库持久化；E3 真实非付费或已授权的远端服务/实际第三方插件；E4 Windows Electron安装、交互、ACL、休眠、系统重装。每个结论记录实际达到的最高级别与缺失层级，不能以E0/E1替代E3/E4。跨模块场景由测试负责人管理组合验收，但缺口按owner模块归并，后续实现任务仍按模块分发；实际产品未落地时只执行能取得真实证据的实验。

**优先补证路线**：先以H11/H12/H13/H14/H15作为完整用户行为骨架，再用H01–H10/H16–H20叠加扰动；不必跑遍所有笛卡尔组合，采用风险优先的成对组合、权限与副作用临界窗口重点检查。特别注意：H15需要真实远端测试仓库和授权，不得在生产仓库进行破坏性冲突注入；H19/H20涉及数据清理/迁移时只能用隔离副本，不触碰用户实际目录。所有未批准的付费模型调用、破坏性删除、跨机器敏感操作均不得执行。

### 日志系统专项：架构缺口与后续契约设计输入

当前仓库有日志目录、诊断、Operation回执、授权审计及输出脱敏的零散约定，**尚无独立成体系的日志/可观测性业务契约与生产实现**。H19涉及容量，H21补齐从设置、产生日志、检索、导出到故障恢复的完整用户链路。不得把现有日志提及当作“已实现日志系统”。

- **分四种记录**：①调试/运行日志（可轮转、清理），②操作尝试与回执（connections权威），③权限批准/拒绝/撤销审计（permissions权威），④任务、产物核验、验收记录（workflows权威）。可通过关联标识联合查询，但不能复制权威状态到通用日志里做第二份账本。
- **共同诊断信息（候选）**：发生时刻与时区、来源模块/实例/版本、严重级别、动作与关联（Context/Conversation/Task/Operation/attempt/插件进程的获准标识）、可见错误分类、耗时、资源版本和脱敏消息。敏感正文、Key、Authorization头、未经授权的完整路径/文件内容不应默认记录。跨进程时间与顺序不能仅凭墙上时钟排序作事实证明。
- **归属候选**：先评估在`shared`提供轻量通用日志机制并由各模块自己产出结构化事件；`app`仅装配/启动捕获；`UI/settings`提供权限受控查看/导出；`permissions`决定可见范围与审计；独立插件宿主、Agent子进程的stdout/stderr必须限量、标记不可信来源并做脱敏。只有真实需求证明必要时才新增独立`logging/`功能域，不提前创建目录或二套持久化服务。
- **设计和验收必问**：数据根不可用时日志退化到哪里、是否允许最小系统启动诊断；日志异步丢失与操作审计写入失败分别怎样影响操作安全；日志级别/保留期/大小上限/备份/清理策略；跨进程关联及崩溃前最后记录；用户手动导出与分享时的脱敏；多用户与插件恶意输出的隔离；撤权后日志缓存及导出权限。安全审计的持久性与普通日志轮转分开，不默认把所有用户操作原文长期保存。
- **最小证据分级**：E0静态评审归属与权限；E1故障注入测试日志失败/脱敏/轮转；E2真实Node子进程并发日志与崩溃前后回读；E4 Windows Electron多窗口/多用户、实际路径失联/日志包导出。只有运行测试与保留的结果才能声明相应等级通过。
