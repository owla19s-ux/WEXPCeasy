## 1. 研究背景与边界

WEX 的长期目标之一是：用户用自然语言提出产品意图，AI 协助将其转化为可实现、可验证的产品、架构、模块、接口、施工任务与交付成果，并逐步实现单人加 AI、多 AI 的可靠协作。早期采用“源码目录 + 公共接口”的模块化理解，同时要求 AI 独立按模块施工，实际暴露出模块依赖、跨模块改动、并行 PR、任务层级以及测试与设计相互越权的问题。

**基本判断：**0.1.1 是基础平台，不是完整多 Agent 软件工程系统。既有代码和测试是可复用资产；发现潜在风险不意味着现有架构需要立即推翻。AI 可降低代码修改成本，但接口兼容、数据迁移、用户数据、Operation 回执仍须谨慎。

## 3. 2026-11-08 源码观察（静态证据，非性能结论）

以下观察针对当时的 WEXPCeasy 基线 `675d354fae58a60dd32800ba5e741d1f99949bae`；后续变更须重新核对：

- `Space` 主要管理 Context、地址、资源引用与配置选择；不是文件和模型数据的统一中转站。
- `connections/api/src/transport.ts` 自行处理 HTTP/SSE，并通过公共 Operation 账本记录相关结果；并非所有流式片段必须经通用 Connections.invoke。
- `connections/src/operations.ts` 的状态结构为完整 `operations[]`，读、修改和提交涉及整个集合；存在随数据量增长的成本，尚无本轮性能测量。
- `connections/src/capabilities.ts` 和 `connections/src/dispatch.ts` 的通用参数/结果主要采用 JSON、规范化及复制；大数据结果或许需要引用/流式机制，具体方案未定。
- `app/src/desktop-authority.ts` 的共享 `busy` 限制同窗口部分业务请求重叠；底层 Connections 的 `pending` 集合并不等价于“只能运行一个连接器请求”。
- 当前桌面部分文本写入入口有约 1 MiB 输入限制，API SSE 解码路径也有独立字节上限；这些限制不能当成公共层总体吞吐能力的测量。

## 4. 研究和变更纪律

1. **先研究、后实验、再决策**：分别确认实际调用路径、负载、瓶颈、用户场景与迁移代价。静态疑点不等于已确认故障。
2. **避免新一轮过度设计**：不默认引入消息队列、分布式服务、第二套连接总线或完整 Agent 调度器。
3. **分清权威**：A0 仅保存候选与证据；正式产品设计在 A1，版本工程状态在 A2，模块行为以其当前正式文档及源码为依据。A0 不向 Codex 直接下达施工指令。
4. **不擅自扩大权限或范围**：任何接口、数据结构、权限语义、模块归属及版本范围的调整，须在研究和确认后单独处理。
5. **未来实验建议**：以隔离环境分别测量 Operation 数量/回执体积、连接器并发、Context 资源引用、长时间模型流、UI 操作占用与取消恢复；报告应注明测试 SHA 和方法，不自动触发大范围重构。

## 6. 2026-11-08 补录：Space / Context、模板、多视图与自由格子的产品构想

> **记录边界**：本节整理用户对 WEX 长期方向的解释、历史思路与后续研究题目；不代表已完成技术选型或 0.1.1 开发授权。下列“应区分”的术语是避免误读的研究口径，不新增强制数据模型。

### 6.1 发展脉络与核心目标

- 从移动端 AI+、早期维加、APS、Android WEX 到 WEXPC/WEXPCeasy，用户始终关注的是**能够适应不同工作方式的人机交互协作组织空间**，而不是把所有工作收敛成 AI 聊天客户端、项目管理或单一 Agent 工作流。
- 早期维加已有概念雏形但范围过大；在 2026 年 9 月中旬至 10 月中旬的反复研究中，连接、权限、对话、Space/Context 等基础边界逐渐清晰。此为用户对设计历程的回顾，非逐版本的工程完成证明。
- **术语采用 Space、Context**；不将 Context 直接命名为“项目”或用普通对话“上下文”语义替代。Context 按已有 Space 方向理解：**引用、组织、关联资源和能力，支持不同展示与交互视图**；它不等于资源文件本身、聊天窗口或特定模板。

### 6.2 自由格子原始构想：自由布局与稳定关联

- 源于对传统树形/扁平结构展示不足的观察：以一个产品或核心对象为中心，功能、模块及其子对象可以向四周自由展开，也可在多个层级中形成横向和跨层关联。
- 早期采用表格网格及 A1、B5 等编码作为简单、可读的定位/绑定线索，让用户和 AI 能定位格子并建立父子、依赖、引用等关系。**移动视图中的方块不能使既有关系失效**。
- 待研究：区分稳定对象身份、可变视图坐标/格子编码、实际资源地址及对象间关系；尤其考虑源码目录迁移、Git 版本变化，以及同一对象在多个视图中呈现。不得把“格子坐标即永久身份”直接当成已确定方案。
- 软件工程示例存在需求/功能表、架构层、模块、源码目录、模块文档、代码、测试和产物等不同层次；可把它们想象成各层独立摆放、又能跨层连接的“方块堆”。层级并非只允许一对一或相邻层连接。

### 6.3 多视图、工作流与模板并非同一概念

- **多视图**关注同一 Context 中被引用对象与能力的不同观察和交互方式；一个 Context 可同时有多个视图，未来需研究布局保存、对象映射和状态联动，但不提前冻结 UI。
- **自由格子**侧重对象布局和关系组织；**工作流**侧重执行依赖、输入输出、并发/分支及运行状态。某些工作流只需观察一个节点，另一些需要多个节点同时实时预览，也可能存在多个子流程的线性与堆叠。不能把一切依赖箭头视为执行箭头。
- **模板**是适配某种工作模式的组合，而不是 Context 本体或一张预绘好的工作流图。可按需要组织资源/能力引用、关系、视图和工作流；不要求所有模板具有同一结构，更不要求任何模板都必须启动执行任务。
- 视图类型可因领域而异：软件开发有自由格子/架构/源码/验证；小说世界有地图、人物、地点、事件、时间线与轨迹（故事内时间与创作执行时间不同）；视频制作有时间线、流程、多个实时渲染预览；角色系统涉及 3D/声音/动作/表情资产、AI 决策、语音及实时同步。虚拟角色与底部交互栏也可构成一种 Context 交互视图，而不是另外发明一套 Context。

### 6.4 外部能力复用与专业闭源风险

- 优先引用成熟软件、库、模型、编译/渲染工具，不将完整视频剪辑器、3D 软件等专业产品默认纳入 WEX 自研范围。
- **软件能连接，不等于其能力可组合**：还取决于结构化控制、输入输出兼容、实时预览、进度与错误反馈、恢复/并发、专业格式与时序同步。某些专业软件即使能够启动或导出，也不一定开放内部时间线或渲染节点。
- 商业软件可能限制接口、收费或变化，具体程度待证实；要研究能力降级、替代和开放标准，避免单一厂商锁定。必要时可能自研**缺失的关键组合/同步/预览能力**，但不等于自研整个专业软件。
- 后续重点验证不同能力的接入深度，以及模板、视图、外部专业工具与 WEX 公共连接/Operation 边界如何配合；不能把所有大媒体数据强行经由通用消息通道复制。

### 6.5 待研究而非当前施工

1. 从早期表格编码原型到稳定身份与跨层关系的最小实验；比对现有画布库与文件/对象引用模型。
2. 同一 Context 的多视图同步、独立布局和跨视图导航；只做场景原型，不急于定义宿主协议。
3. 视频多节点实时预览、小说地图时间联动、实时角色资产与运行三类差异很大的试验，以检验“模板组合”抽象是否过度统一。
4. 外部软件接口成熟度、可替代性、数据格式/时序及必要自研的边界评估。
