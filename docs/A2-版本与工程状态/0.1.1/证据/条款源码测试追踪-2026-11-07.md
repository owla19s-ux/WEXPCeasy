## A. 总账使用规则

1. **链路**：历史条款（仅溯源）→ 用户/后续决定与正式版本计划 → 当前领域 owner → 公开源码 → 具体测试文件/执行回执 → 已验证的范围与缺口。
2. **状态词**：`部分实现` 只表示有代码或局部测试范围，绝不等于本次测试通过或用户验收；`未验证完整实现` 不能解释为确认“完全没有”；`延期` 非已删除需求；`政策已确认 / 未完整实现` 不代表权限可自动开放；`历史方案已替换` 仅指有直接依据的冲突项。
3. **测试列**列的是具体可检查文件与有时目录 glob，**不是报告本轮测试通过**。需要判“通过”必须记录命令、运行时间、完整结果、对应 SHA、受测环境；Windows E4 独立报告。
4. **源码列**使用源文件/符号定位；括号标“未找到”仅说明本轮检查的公开入口不存在，不构成全仓不存在证明。历史契约若含候选 schema、权限、Placement、运行节点等，不得由 Codex 直接照单编译。
5. **施工决策**：只修本版已确认范围内的真实缺口。高风险、跨 owner、新数据模型和未决版本划分应先在对应决定/版本文件裁决，不能由总账赋权。

## D. 明确裁决和待裁决的边界

- **已确认，不应重开**：Space/Context 不增加产品级 Placement；`environments/` 独立于 Local/Connections；0.1.1 不引入自由格子工作流、Scheduler、DSH 插件系统和 DSH 连接器；UI 本版采用已更新的动态工作窗口设计而不是旧固定四列。
- **已确认政策，不等于已实现**：D01/D02 四级与工作流启动方案；当前基础受限 local 授权路径已经实现，Task/Callback 仍安全阻断。特殊信任根、Windows IPC、有限次数/竞争控制不得凭 IV 级自动放行。
- **需要单独判断**：Conversations 本版基础段落编辑 vs CV-05/15/16 完整分支/采纳，GitHub GH-01～12 本版必要范围 vs 长期官方覆盖，环境 F06-009/010 有限识别/选择 vs 完整安装器，以及 Views 专业引擎与基础多标签 UI 的验收分界。
- **技术事实不能回填产品决定**：源码目前的单组织关系只描述当前模型，不凭它替用户裁定多 Space 引用的长期语义；历史 runtime 草案不能废除后续独立 Scheduler owner。
