## 模式分工

- **工作模式负责施工**：检查最新 `main`、模块现有实现与测试，按模块 README 规定的范围补齐代码、修复问题、运行测试并提交。**禁止修改任何施工文档**，包括根 README、模块 README、CONTRACT、任务计划与研究文档。发现文档错误、需求冲突或未决事项，在回执中说明，不自行改写。
- **普通对话模式负责检查与验收**：核对代码、接口、测试证据和施工回执；更新模块 README 的已实现、已验证、未完成与阻塞状态；验收通过后再更新本文件的当前模块入口。
- 施工回执至少包含：提交 SHA、修改的代码与测试文件、实际运行的测试及结果、未验证项、阻塞事项。**提交成功不代表验收通过。**

## 模块化施工规则

1. **单模块施工**：以当前模块的职责和公开接口为边界，先查已有代码，再实现未完成的稳定功能；不要因为历史文档写着“待实现”就重写已有成果。
2. **模块独立**：业务数据和行为归所属模块维护；跨模块通过公开能力协作，不建全局业务状态总管，不把业务逻辑堆到 `shared/`。
3. **链路不作为施工单位**：跨模块业务链路只用于需求核对及后续组合验收；不按链路把多个模块混在一起施工。
4. **不擅自扩展**：未批准的候选契约、实验结论和历史计划不是施工命令；重大产品决策、权限政策和模块边界冲突需报告。
5. **安全边界**：未授权入口默认拒绝；模型输出、角色名称、Context 关联和工具可见性不构成授权。
6. 当前是**单 AI 施工**，不额外引入多 AI 派工、锁定或并发协调流程。

## GitHub 操作与测试

- 默认在 `main` 施工。写入前检查最新 HEAD 和已有变更；只有确需风险隔离时才建立短期分支。
- **检查 CI 先看 [Actions 总工作流运行列表](https://github.com/owla19s-ux/WEXPCeasy/actions/runs)**，核对最新运行集合、关联提交 SHA、状态和结论，再查看对应 workflow、job 与失败日志。不要只看固定工作流或旧运行记录，也不要让用户反复提供链接。
- 可以运行必要的 GitHub Actions 测试。失败先查原因并修复，不盲目重跑；CI 绿灯不能代替模块验收或 Windows 实机验证。
